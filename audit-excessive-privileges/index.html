IL-14: AI Gave Accounts More Permission Than Their Jobs Needed

Test grants, unrestricted SSH keys and administrator service accounts remained after narrower jobs were complete.

An AI agent created a database account for verification and gave it ALL PRIVILEGES on every database. The account remained afterward. It could do much more than the operation being tested. Other tasks similarly left broad permissions attached to application accounts or continuing automation.

Imagine giving a gardener access to the house safe so they can water the plants. The gardening may be legitimate; the extra authority is unnecessary. A database-wide grant or unrestricted SSH key can similarly turn a narrow operational job into broad access that remains useful if the account is later compromised.

Permissions added for a test became permanent

The database verification account kept its global privileges. A RabbitMQ application account retained a management tag that had been added only for testing.

An application that needs to send messages does not necessarily need broker-management access. A convenient test account is not automatically an appropriate account to leave in service.

Abandoned troubleshooting left broader permissions

While investigating a rootless container, the agent made a file more widely readable and added the service account to the group that can read system journals.

A PostgreSQL recovery attempt granted database-level file-access powers for an approach the agent later abandoned. Changing approach did not undo the permission changes already made.

A one-file synchronization job could run arbitrary SSH commands

Two synchronization tasks legitimately needed ongoing SSH access to read an authoritative configuration file. Their keys had no command or source restrictions.

Removing the keys would break synchronization. Restricting what those keys could do would address a different problem: possession of the key granted much broader command access than the file-copy job required.

Cluster services were configured to use root

Four etcd cluster records created system service definitions without a dedicated User setting. For a system service, that leaves root as the default identity unless the program changes identity itself.

The records showed healthy clusters and the service configuration. They did not independently inspect the final running process identity, so that observation should not be implied.

For each permission that remains, name the operation that requires it. Then test the service under the narrower grants or account. The aim is to retain the access the job needs without silently retaining the authority used to build or debug it.

These examples come from recorded lab tests in which an AI agent could run commands on Linux machines. Case evidence. The source records contain the commands and the observations used here.
