AI Granted Service Accounts More Access Than Their Jobs Needed

Verification grants, broad SSH access, troubleshooting permissions and daemon identities exceeded their continuing roles.

A test account needed one database operation and received access to every database. A synchronization key needed to read one file and retained unrestricted SSH command access. The continuing job could be legitimate while the authority granted to do it was much broader than necessary.

Imagine giving a gardener access to the house safe so they can water the plants. The gardening may be legitimate; the extra authority is unnecessary. A database-wide grant or unrestricted SSH key can similarly turn a narrow operational job into broad access that remains useful if the account is later compromised.

Verification permissions became application permissions

A verification account received ALL PRIVILEGES on every database and was retained. A broker application account kept a management tag introduced only for testing. These grants exceeded their final application roles without proving a remote exploit. (first trace; second trace.)

A database-wide grant or broker management tag can make a test convenient.

An abandoned recovery path kept its grants

Rootless-container troubleshooting broadened a file’s readability and added the service account to the journal group. A PostgreSQL recovery attempt granted file-access powers for an approach later abandoned. Those permissions survived the change of plan. (first trace; second trace.)

Troubleshooting can broaden group membership, file readability or database file-access powers.

A continuing SSH job had unrestricted command access

Two configuration-sync tasks retained SSH keys without command or source restrictions. The keys were needed for ongoing synchronization; the concern was unrestricted command access for a job described as reading one authoritative file. (first trace; second trace.)

These synchronization keys have an ongoing purpose, so simply removing them would break the task.

A daemon inherited administrator identity

Four records configured three-member etcd clusters without a dedicated service user. The service definitions therefore retained the default root identity. Health checks established cluster operation, but did not independently sample the final daemon identity. (commands.)

Four remaining entries describe etcd service definitions on three-member clusters with no dedicated user setting.

What should an administrator check?

The review should connect each retained permission to an ongoing operation. It should also distinguish configuring a service identity from observing the identity of its running worker. Reducing authority requires arranging the necessary file and runtime access, then repeating the functional checks under that narrower account.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines.
