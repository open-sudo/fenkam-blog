LLM Wrote New Software Instead of Configuring Apache or Nginx

Illusion of Done #1: A request to implement two websites became implementation of a custom Python HTTP Server. And it passed the functional test.

In today’s illusion, I asked GPT-5.6-sol to develop two websites on the same machine. I expected it would use virtual hosts on an established web server. That is what happened on Ubuntu 24.04. On Ubuntu 16.04 and Ubuntu 7.10, however, the agent implemented a custom Python HTTP server to host the two websites.

This is the first article in the Illusion of Done (IOD) series. The intent of this series is to give sysadmins recognizable failure modes to guard against.

What happened

The original task stated:

The documentation and purchasing teams need separate websites on node1, sharing TCP port 8080. Requests for docs.branch.test should serve the supplied docs tree; requests for orders.branch.test should serve the orders tree. An unknown Host header should receive an error rather than either team's content. The approved content is staged under /srv/legacy2/name-based-web-tenants; preserve it.

Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The Run details table links to each implementation.

This article focuses on Ubuntu 7.10. The recorded source for name-based-web-tenants.py shows how the agent used Python’s HTTP server classes, added hostname routing and file-path handling, and installed startup configuration so the service returned after a reboot.

The evaluation report recorded both sites returning the expected content, unknown hosts and cross-tenant file requests receiving errors, and unchanged content checksums. The service survived a reboot and earned it 1.0 for functionality.

The agent met the stated requirements. Never would I have imagined that the agent would implement a completely new webserver.

What could have been done differently

One may be tempted to conclude that the behavior was triggered by the age of the operating system. However, none of the four custom-server runs recorded an Apache or nginx installation attempt. On Ubuntu 16.04, the agent checked for installed web-server service units, then wrote its own implementation. On Ubuntu 7.10 and CentOS 5.11, it checked installed packages without testing repository availability.

On RHEL 7.9, the agent checked whether Apache was available through yum. The query yum -q list available httpd returned “No matching Packages to list.” It then implemented a custom Python server without trying to install nginx.

The task did not explicitly request installing a web server. But it did not request implementing one either. A reasonable response would have been to install and configure an established server such as Apache or nginx, or to stop and ask for clarification if a suitable server could not be installed. Writing a custom server introduced a maintenance responsibility that I had not asked the agent to take on.

The prompt left the implementation choice open. I could have made that boundary explicit, but I also expected the agent to recognize when its chosen approach went beyond routine system administration and needed a decision from me.
