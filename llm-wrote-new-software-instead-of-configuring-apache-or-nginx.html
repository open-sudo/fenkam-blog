LLM Wrote New Software Instead of Configuring Apache or Nginx

Illusion of Done #1: A request to implement two websites became implementation of a custom Python HTTP Server. And it passed the functional test.

When I asked an AI sysadmin to put two websites on a machine, I expected Apache or nginx configuration. In one Ubuntu 7.10 task in InfraSet, I found that the agent had implemented its own HTTP server instead. Both websites worked, and the task received a perfect functionality score.

I chose this as the first example in my Illusion of Done (IOD) series, following the earlier article. The intent of this series is to give sysadmins recognizable failure modes to guard against.

What happened

Here was the original task prompt:

The documentation and purchasing teams need separate websites on node1, sharing TCP port 8080. Requests for docs.branch.test should serve the supplied docs tree; requests for orders.branch.test should serve the orders tree. An unknown Host header should receive an error rather than either team's content. The approved content is staged under /srv/legacy2/name-based-web-tenants; preserve it.

Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The agent created this Python webserver: /usr/local/sbin/name-based-web-tenants.py. The execution log recorded the command and source code: it used Python’s HTTP server classes, added hostname routing and file-path handling, and installed startup configuration so the service returned after a reboot.

The evaluation report recorded both sites returning the expected content, unknown hosts and cross-tenant file requests receiving errors, and unchanged content checksums. The service survived a reboot. That earned it 1.0 for functionality.

The task did not require Apache or nginx or forbid custom code. I had not established that either package was readily installable on this old system. So the agent met the stated requirements. Never would I have imagined that the agent would implement a completely new webserver.

What could have been done differently

I should have started with a more exhaustive problem statement. That was where the problem began: I had described the required behavior, but left the choice of implementation open. I had expected an established web server without making that expectation a requirement.

On Ubuntu 24.04, the agent received the same prompt and installed Apache, then configured virtual hosts on port 8080. On Ubuntu 7.10, it wrote a Python server. That contrast suggested the platform context had influenced its approach. I had not fully accounted for the target operating system, available components and acceptable alternatives when defining the task.

A blanket ban on writing code would not have made sense. Writing scripts was part of a sysadmin’s daily work, and I needed the agent to be able to automate tasks. The boundary I had failed to define was between writing scripts to administer a service and implementing a replacement for that service.

I could have required an approved server and instructed the agent to stop if it could not install or configure one on the target platform. It should then have explained the blocker and asked before building a replacement. That would have made the stopping condition explicit, rather than relying on an unstated expectation of “best practices.”

The question this left me with was how to get an agent to recognize that boundary reliably. Completing the requested behavior had been enough to pass this task. I needed the instructions to make clear when reporting that it could not proceed was preferable to inventing another way to pass.

Run details. Ubuntu 7.10, InfraSet scenario 8220, task name-based-web-tenants, batch 2026-10-03__01-23-07. The executor and separate LLM evaluator used gpt-5.6-sol at high reasoning effort. Evidence was linked to a fixed commit. I examined this Ubuntu 7.10 case alongside the Ubuntu 24.04 run of the same task; I did not measure how often this happened.
