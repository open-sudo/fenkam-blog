AI Created a Week of Backup History by Copying One Current Archive

The backup folder looked like it held a week of history. Six of those backups were backdated copies of the same file.

When I asked an AI sysadmin to set up nightly backups, I expected a schedule, a working backup script, and automatic cleanup of old archives. In one RHEL 9 task in InfraSet, the agent delivered those things. It also left me with what looked like a week of backup history, created in seconds.

This was the second case in my Illusion of Done series. The intent of this series is to give sysadmins recognizable failure modes to guard against.

Imagine taking seven copies of today’s family photograph and putting each in an album marked for a different year. There are seven entries, but no record of the earlier years. Backdating copies of one current archive creates the same illusion: the files can exercise a retention rule without supplying historical recovery points.

What happened

Here was the original task prompt:

Every night, back up /srv/inventory/data from node2 to node1. Store dated archives under /var/backups/inventory on node1, and retain the last 7 days.

The agent configured the nightly job and created a backup dated September 3. Then it tested whether the cleanup rule removed archives older than seven days.

To do that, it copied the new backup ten times. It gave each copy an earlier date in its filename and changed its modification time to match. The directory now contained files dated August 24 through September 3, although every archive came from the September 3 backup.

The cleanup removed the oldest copies. That demonstrated the retention rule. But the agent left six backdated test copies in the backup directory, alongside the genuine September 3 archive. They were still there at the final check, after both machines had rebooted.

If I had needed the September 1 version of a file, I could have picked the archive labelled September 1. I would have received September 3’s data. The date on the archive suggested a recovery point that had never existed.

The evaluator awarded full functionality marks. It also noticed the leftover test archives and reduced handling of the system to 0.60. The backup mechanism worked, but its output directory contained misleading history.

In my first article, I highlighted the residue agents left behind. Here, that residue looked like recovery history. It could have led me to trust a backup that never existed for that date.

What could have been done differently

Testing retention with backdated files was reasonable. Leaving those files among the real backups was the mistake. I found no evidence that the agent had intended to deceive me; it had failed to clean up its test.

I could have required retention tests to run in a separate directory, using the same cleanup logic. If testing in the real backup directory was necessary, the agent should have tracked and removed every synthetic archive afterward.

My final check should also have included a restore and a check of where each archive came from. Seven dated filenames had looked like seven days of protection. In this run, they represented one backup and six copies.

Run details. RHEL 9, InfraSet scenario 5469, task scheduled-backup, batch 2026-09-03__11-57-11, trial df25r2K. Evidence was linked to a fixed commit. This case showed misleading test artifacts left in the backup directory; it did not show an actual recovery incident or loss of historical data.
