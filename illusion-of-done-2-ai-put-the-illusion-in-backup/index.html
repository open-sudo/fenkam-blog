IL-2: AI Left Six Backdated Copies of One Backup

The retention test worked, but six backdated copies stayed beside the only genuine backup.

I wanted nightly backups between two RHEL 9 servers, retaining seven days of archives. Because this was a new setup, the agent also needed a way to test deletion of old files without waiting a week.

The AI agent copied the September 3 archive ten times and gave the copies earlier filenames and modification times. That provided synthetic history for the retention test.

The deletion test left false recovery dates behind

Cleanup removed the oldest test files. After the test and reboot, six backdated copies still sat beside the genuine September 3 archive. The listing appeared to hold a week of recovery points.

The dates were not the dates of the data. Choosing a file labelled September 1 would return September 3’s contents. The backup schedule could work correctly while that directory misrepresented the history available.

Seven copies of today’s family photo do not show what the family looked like seven years ago. Giving an archive several dates does not create earlier versions of its contents.

Testing retention and building real history were separate jobs

There was nothing wrong with creating dated test inputs to exercise deletion. Those inputs needed to be kept apart from real backups, or removed before the archive set was handed over.

A newly configured job could legitimately have only one genuine backup. The operator needed that fact, rather than a directory where test copies looked like earlier recovery points.

The useful final check was a restore that inspected the returned contents. Counting dated filenames could not establish which points in time were actually recoverable.

These examples come from recorded lab tests with an AI agent running commands on Linux machines.
