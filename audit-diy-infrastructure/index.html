IL-15: AI-Written Proxies Handled the Demo but Missed Other Requests

Generated HTTP proxies and DNS forwarders omitted behavior that a simple successful request did not exercise.

An AI agent wrote a small HTTP proxy, then verified it with a page request. The page loaded. The code, however, handled only GET and HEAD and read whole responses into memory. That demonstration did not show how it would handle a form submission, a large streamed response or a client whose login headers needed forwarding.

Imagine replacing a town’s postal sorting service with a homemade chute that delivers one standard envelope. The demonstration succeeds, but parcels, signed deliveries and returned mail still need handling. Generated proxies and forwarders can have the same gap: a simple request works while less visible protocol obligations remain unimplemented.

The HTTP implementation handled only part of the traffic

Two generated proxies supported only GET and HEAD and buffered complete response bodies. One sent an upstream GET when its client requested HEAD, and dropped authorization or cookie headers.

Those details change application behavior. A site’s public page can load while an authenticated request or another HTTP method fails. The examples establish omissions in the code, rather than an observed failure of every kind of request.

Retrying a write could repeat the operation

Another proxy retried a POST on a different backend after a broad exception. It did not check whether repeating the request was safe.

A backend could finish a write and then lose the connection before its reply reached the proxy. Retrying could submit the same operation again. No duplicate write was observed in this test; the problem was the unguarded retry in the delivered code.

A DNS answer was accepted without all the expected checks

Two generated DNS forwarders passed back UDP replies without matching both the expected sender and request identity. They also lacked an upstream TCP retry when a UDP answer was truncated.

Resolving one internal name did not exercise those cases. A successful lookup could coexist with an answer-validation weakness or failure on a larger response.

If the task requires an existing product, substituting new software is already a change to discuss. If custom software is permitted, its supported behavior still needs to be explicit. A working demonstration is the start of that review, not a substitute for it.

These examples come from recorded lab tests in which an AI agent could run commands on Linux machines. Case evidence. The source records contain the commands and the observations used here.
