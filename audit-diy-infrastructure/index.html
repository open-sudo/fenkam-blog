AI Built Proxies That Passed Simple Tests but Missed Protocol Behavior

Custom HTTP proxies and DNS forwarders met narrow demonstrations while leaving production behavior incomplete.

A generated proxy forwarded the demonstration request, but did not implement every behavior a client might expect from a load balancer. A generated DNS forwarder resolved an internal name while omitting important validation. The narrow demonstration and the completeness of the implementation were different questions.

Imagine replacing a town’s postal sorting service with a homemade chute that delivers one standard envelope. The demonstration succeeds, but parcels, signed deliveries and returned mail still need handling. Generated proxies and forwarders can have the same gap: a simple request works while less visible protocol obligations remain unimplemented.

HTTP proxying narrowed the supported behavior

Two generated HTTP proxies supported only GET and HEAD and buffered entire response bodies. One also turned HEAD into an upstream GET and dropped end-user authorization or cookie headers. A simple successful GET did not exercise those behaviors. (first trace; second trace.)

A proxy that handles the demonstration GET can still omit other methods, change HEAD semantics or lose authorization and cookie headers.

Retries changed the meaning of a write

A generated proxy retried POST on another backend after a broad exception, without an idempotency check. A backend that committed before the response failed could therefore receive a repeated mutation. No duplicate transaction was observed. (commands.)

A backend may commit an operation before the proxy loses the response.

A DNS response arrived without the expected validation

Two generated DNS forwarders returned upstream UDP responses without checking the expected source and request identity. They also lacked truncation-triggered upstream TCP fallback. Resolving the demonstration record did not test either weakness. (first trace; second trace.)

Returning an upstream UDP packet without matching its source and request identity creates a different assurance from resolving one internal name correctly.

What should an administrator check?

Where the request specifies an established product, an unauthorized replacement is already a material problem. Where a new or demonstration service is permitted, its limited implementation still needs to be described honestly. The inspected code supports these protocol concerns; it does not establish that every conditional production failure occurred during the tests.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines. The source extract includes all 9 cases grouped under this topic, their commands and assessment references, and the limits of each finding. The article distinguishes observed failures from risks identified in code and behavior that was not tested. No production attack is claimed. Original records are available in InfraSet.
