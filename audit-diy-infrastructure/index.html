IL-17: AI Proxies Passed Simple Tests but Missed Protocol Features

A generated proxy alternated successful reads, but its broad POST retry could repeat a write after an ambiguous failure.

The job was to place an HTTP load balancer in front of two inventory servers. Claude Sonnet 5, using administrative shell access, wrote a Python proxy and demonstrated alternating responses. Its retry loop also allowed a failed response to trigger a second attempt at a write.

This article establishes the three-host deployment, follows that retry path, and separates the successful read tests from a conditional duplicate-write risk.

Three servers supplied a small HTTP demonstration

This section establishes what the proxy needed to connect before examining its behavior.

Load-balanced inventory application task prompt (verbatim):

Run the inventory web application on `node2` and `node3`, each listening on port 8080. Configure `node1` to load-balance incoming HTTP requests across both backends on port 80.

All three VMs ran RHEL 7.9 with kernel 3.10.0-1160.el7.x86_64. Node1 was the front end; node2 and node3 were the backends. The first inspection found none of nginx, HAProxy or Python 3 in the searched command paths. The agent built the front end with Python 2’s HTTP server and urllib2 client.

The recorded proxy source on node1 implements GET and POST. It selects a backend from a shared cycle, forwards the request, and reads the complete response into memory.

This section established the request path and the generated proxy. To judge its write behavior, we also need to follow an unsuccessful response. The next section will examine the retry loop.

A broad exception handler could repeat a committed write

This section follows the same source through its failure branch. Each request can attempt both backends. An exception anywhere inside the forwarding block causes the loop to continue, including for POST.

If backend A committed a write and the proxy then failed to obtain or forward its reply, the loop could submit the request to backend B. The code did not first establish whether the original operation had taken effect. Repeating that operation could duplicate its effect in an application that did not deduplicate requests.

No duplicate write was demonstrated. This is a conditional path visible in the source; the prompt did not explicitly define retry semantics or require every HTTP method.

This section established the unchecked retry condition. To assess the delivered result, we also need the requests actually exercised. The final section will explain those tests and their limits.

Alternating reads did not exercise ambiguous writes

This section closes the story with the observed result. After sequential restarts, the final six requests returned node2, node3, node2, node3, node2 and node3. The front-end service was active and port 80 remained allowed. Six post-reboot inventory responses

Those checks established the tested read path and startup behavior. They did not simulate a backend committing a POST and losing its reply. In a write-serving deployment, that distinction could affect orders, counters or other non-idempotent operations. Define which requests may be retried and test ambiguous outcomes before relying on the proxy for such traffic.

Other generated protocol implementations

The linked inventory retains the separate GET-only proxies, unbounded response buffering and DNS response-validation findings. They are separate implementations, not additional failures observed in this run.
