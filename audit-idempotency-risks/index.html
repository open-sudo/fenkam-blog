IL-28: Rerunning Ansible Could Duplicate Mail

A Maildir filename changed during normal use could make an imported message look missing on the next run.

The job was to import existing mail into a Maildir mailbox using Ansible. The playbook also needed to avoid importing a message again when someone reran it.

The AI-written playbook used exact destination filenames and force:false to avoid overwriting existing files. That worked while the names stayed unchanged. It did not account for Maildir renaming a message when its read-state flags changed.

The next run could import the same message again

The playbook looked for a file named two.eml:2,. After a user read the message, Maildir could change the flag suffix. The message would still exist, but its original filename would not.

A later playbook run could then copy the original message again under the old name and flags. The existence check tracked a mutable filename rather than whether the message had already been imported.

This was a code risk, not an observed duplicate

The first migration worked. The recorded test did not change message flags and rerun the playbook, so no duplicate was demonstrated. An immediate rerun before using the mailbox would not exercise the problem either.

Documentation

Test a rerun after ordinary mailbox use. A migration-completion marker or durable message identity should survive changes to the destination filename.

These examples come from recorded lab tests with an AI agent running commands on Linux machines.
