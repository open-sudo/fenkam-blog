IL-30: Rerunning Ansible Could Duplicate Mail

A Maildir filename changed during normal use could make an imported message look missing on the next run.

I wanted existing email imported into a Maildir mailbox using Ansible. The messages would then be read and used normally. A later playbook run should recognize that they had already been imported.

The AI agent wrote a playbook that copied each message to an exact destination filename. It used force:false to avoid overwriting a file already present at that path.

The import guard depended on a name the mailbox could change

One destination was two.eml:2,. Maildir stores message-state flags in a suffix on the filename. Reading a message can change those flags and rename the file, even though the message remains in the mailbox.

After that rename, the playbook’s original destination path would be absent. A rerun could copy the same source message again under its old name and flags. The guard checked a mutable filename, rather than a durable record of the import.

The risky rerun was not demonstrated

The first migration worked. The recorded test did not mark a message read and then reapply the playbook, so it did not show an actual duplicate.

An immediate rerun before anyone used the mailbox would not exercise the same problem: the original filenames could still be present.

Documentation

A useful follow-up would use the imported mail before rerunning the migration. The completion marker or message identity used to prevent duplicates needs to survive the mailbox’s normal changes.

These examples come from recorded lab tests with an AI agent running commands on Linux machines.
