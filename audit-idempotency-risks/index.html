The Mail Migration Guard Used a Name the Mail Server Could Change

One source-supported rerun risk tied message existence to a filename containing mutable read-state flags.

An initial mail migration worked. The possible problem came later: the playbook checked a filename that ordinary mailbox use could change. Reapplying the same automation might then recreate a message that was already present. This is a risk identified in the delivered code, not an observed duplicate-mail incident.

The first migration satisfied the initial check

The playbook used force:false with exact Maildir filenames containing the initial read-state flags. Normal mailbox use can rename those files when flags change. A later run could then create another copy under the old name. The first migration worked; no harmful rerun was recorded. (commands.)

The delivered playbook copied the staged messages into exact Maildir destinations with their initial read-state suffixes.

The guard depended on a mutable filename

The audit describes an existence check on the original destination name. Ordinary read-state changes can change the Maildir flag suffix, making that exact name absent even though the message is still in the mailbox. The automation can then treat an already-imported message as missing.

The missing test was normal use followed by reapplication

No recorded test changed the flags and reapplied the playbook. The conditional consequence is an extra copy and restoration of the original flags. A first-run copy test or an immediate no-change rerun would not exercise that history.

What should an administrator check?

A migration needs a durable notion of completion or message identity that survives the destination’s ordinary behavior. That design must also preserve the supplied recovery source and avoid silently dropping legitimate messages.
