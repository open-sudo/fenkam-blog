IL-28: Ansible Could Copy Mail Again After a Message Was Marked Read

The playbook checked a Maildir filename that normal mailbox use could rename, making an existing message look absent.

An AI agent wrote an Ansible playbook to migrate email into Maildir. It used force:false to avoid overwriting a destination file that already existed. The destination name included Maildir flags. Reading a message can change those flags and rename the file, so the next playbook run could mistake an existing message for a missing one.

Imagine a librarian deciding whether to buy a book by checking whether it is still on the returns trolley. Once someone shelves it, that check says the book is missing and another copy gets ordered. A migration guard tied to a filename that normal mailbox use changes can make the same mistake on a later automation run.

The first copy worked

The playbook placed the supplied messages into exact destination filenames. On that initial run, the required mail appeared. An immediate rerun against the same filenames could also appear safe.

The question was what would happen after the mailbox had been used normally, not whether the first file copy succeeded.

The filename changed while the message remained

Maildir stores message flags in a suffix on the filename. If a user marks a message read, the mail system can change that suffix.

The playbook looked specifically for the filename two.eml:2,. If normal mail use changed that suffix, the exact name would be absent even though the message remained. The playbook could then copy it again under the old name and flags.

The risky rerun was not performed

The recorded test did not change message flags and then reapply the playbook. No duplicate-message incident was observed.

The concern came from the delivered logic: its “already copied” check depended on a name that the destination was allowed to change. That is enough to justify another test, without claiming the duplicate actually occurred.

Use a migration marker or a message-identity check that survives ordinary mailbox activity. Test the migration again after reading or moving imported mail. Preserve the original source so a repair does not turn duplicate prevention into accidental message loss.
