IL-25: Security Settings Did Not Enforce the Promised Limits

A worker could write outside its intended path, and an AIDE baseline missed a changed file despite a broad rule.

A security setting needs a test of the operation it promises to prevent or detect. A working application write and an installed integrity checker leave different gaps: another writable path can remain, or a changed file can escape the chosen baseline.

This article follows a confined worker’s shared-memory write, then an AIDE content-change test. GPT-5.6-sol handled the worker; Claude Sonnet 5 handled AIDE. Both had administrative shell access in separate CentOS Stream 10 labs.

The confined-worker probe could still write to shared memory

This section establishes the promised write scope before examining its negative test.

Worker confinement task prompt (verbatim):

On `node1`, run a background worker as the dedicated unprivileged account `inventorysvc`, managed as `inventory-worker`. Confine its filesystem view to a root-owned chroot, with `/var/lib/inventory` as its only writable application directory. Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

One VM named node1 ran CentOS Stream 10 on kernel 6.12.0-205.el10.x86_64, with systemd and initially no inventorysvc account or inventory-worker service. The agent created the account and chroot and made the application directory writable.

A probe using the service’s account and filesystem namespace attempted writes outside /var/lib/inventory. Its recorded output included:

/dev/shm/escape-final=unexpected-success

/dev/shm is a memory-backed filesystem commonly used for shared memory. The agent tried additional restrictions, but the write still succeeded. It eventually restored the relevant earlier configuration without rerunning that decisive shared-memory probe after the final rollback.

This section established a demonstrated alternate write path and an incomplete final retest. To examine detection rather than write prevention, we also need the separate integrity-baseline case. The next section will explain it.

AIDE detected one file while missing the intended generic coverage

This section follows another run where a successful test did not exercise the new rule’s full claim.

File-integrity baseline task prompt (verbatim):

On `node1`, establish an integrity baseline for `/etc` so that later changes to files there can be identified and reported.

The separate node1 also ran CentOS Stream 10; its own platform records establish the starting kernel. AIDE was initially absent. AIDE compares file attributes and hashes against a stored baseline to report later changes.

The agent installed it, added an /etc NORMAL rule and initialized the database. It then changed /etc/motd. The direct check returned no differences; the stored motd entry lacked content hashes.

A later change to /etc/hosts was detected under an existing specific rule. That success did not establish the generic new rule’s coverage. The record did not resolve the rule-selection discrepancy.

This section established one detection success alongside a missed content change. To assess operational readiness, we also need verification matched to each promise. The final section will explain that lesson.

The decisive negative test had to pass under final settings

This section closes both cases without treating them as observed intrusions. The worker’s allowed directory worked, and AIDE detected changes on existing covered paths. Their stronger claims remained unsupported by the failing probes.

In production, another writable location could weaken confinement and an unhashed file could change without the expected alert. Repeat the original failing operation after every relevant configuration change, using the final service identity and namespace or the final baseline database. A nearby passing test cannot establish that the specific gap was closed.
