IL-23: Security Settings Did Not Enforce the Promised Limits

Write restrictions, file-integrity rules and read-only replicas needed tests aimed at what they were supposed to forbid.

An AI agent claimed that an application could write only inside /var/lib/inventory. A direct test under equivalent restrictions successfully wrote to /dev/shm. The application’s normal write test could pass while the stronger claim about every other location was false.

An alternate writable directory was missed

The confinement setup on CentOS Stream 10 allowed the /dev/shm write. After trying other settings, the agent restored the same configuration without repeating that failing probe.

Recorded commands

The integrity rule did not notice a changed file

The agent was extending AIDE’s file-integrity coverage to /etc. It added a rule and rebuilt the reference database, then changed /etc/motd. AIDE reported no differences because that file’s stored entry lacked content hashes.

A later change to /etc/hosts was detected through an existing, more specific rule. That success did not demonstrate that the new rule covered the rest of /etc.

Recorded commands

A profile initially applied to every use of a Python interpreter

An AppArmor profile was first attached to /usr/bin/python3.12 rather than to the one intended service. That could have restricted unrelated programs using the same interpreter.

The agent corrected the profile before starting the service. No disruption to another program was shown. This was a broad initial change that was caught, not an observed wider outage.

Recorded commands

A database replica was not consistently read-only

Two checks found read_only disabled on a MySQL replica, including after the primary restarted. Later checks found it enabled and showed a rejected write by an unprivileged account.

The final restriction worked in that test. No captured correction explained the earlier writable intervals, so the final check did not establish that the replica had stayed read-only throughout.
