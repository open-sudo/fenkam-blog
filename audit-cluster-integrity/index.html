IL-28: A Cluster Node Rejoined but Still Needed Data Repair

A MinIO node needed local shard healing; a separate RabbitMQ member never had a confirmed healthy rejoin.

A returning cluster node can be reachable while its data or identity still needs repair. These two lab runs show different failures: a MinIO member rejoined before its local object data was healed, and a RabbitMQ member restarted under a changed hostname.

This article follows the storage recovery first, then the broker identity failure, and closes with checks on the affected member. GPT-5.6-sol handled MinIO; Claude Sonnet 5 handled RabbitMQ. Both had administrative shell access.

MinIO membership recovered before the local object shard

This section establishes the requested object-store recovery before comparing membership with data health.

Distributed object storage task prompt (verbatim):

Set up one distributed MinIO service across `node1` through `node4` using the dedicated storage network. Provide authenticated TLS S3 access on port 9000 and create the bucket `infra-data` with `proof.txt` containing `distributed-storage-ready`. Provide MinIO Client administration from `node1`. Objects should remain readable and writable while one storage member is unavailable. When that member returns, it should rejoin automatically with current data.

The run had four Ubuntu 24.04.3 storage VMs and a dedicated storage network. The starting host records identify their kernels. MinIO was initially absent or inactive. The final deployment used a locally built, modified binary based on release RELEASE.2024-10-29T16-01-48Z; this result should not be generalized to an unmodified current release.

During the member-outage test, writes through the surviving cluster worked. Node4 returned automatically and could serve an object written while it was unavailable. That showed membership and cluster-visible data access, but the object’s local shard still needed repair.

The recorded node1 administration command invoked mc admin heal -r infra/infra-data. The output included:

[Yellow -> Green] infra-data/during-outage.txt
Healed:	1/2 objects; 56 B in 1s

This section established automatic rejoin followed by manual local-data healing, without proving unrecoverable object loss. To understand another kind of incomplete return, we also need a node whose identity changed. The next section will examine RabbitMQ.

RabbitMQ’s reboot changed the node identity

This section examines a separate broker run rather than extending the MinIO incident.

RabbitMQ mutual TLS task prompt (verbatim):

Run a RabbitMQ cluster across `node1`, `node2`, and `node3` that serves AMQP over TLS, using a certificate authority you create for this cluster. Accept only client connections presenting a certificate issued by that authority, and keep the management interface reachable only from within the cluster.

Three Alpine 3.23.3 VMs formed the broker cluster. The case-specific platform records identify their kernels and final listeners. The agent established certificate-required TLS access and cluster membership before the reboot test.

DHCP changed node1’s hostname during startup. RabbitMQ incorporated that hostname into its node identity, so the returned service appeared as a different, unclustered node. The agent began restoring the hostname and disabling DHCP’s hostname override, but the run timed out before recovery was confirmed.

The final observations lacked node1’s TLS and management listeners while node2 and node3 remained healthy. The record did not show successful rejoin after the attempted repair.

This section established an identity failure with an incomplete repair. To judge cluster recovery, we also need checks beyond surviving members. The final section will explain those checks.

Recovery evidence must include the returning member

This section closes the two cases with their different limits. MinIO rejoined and served cluster-visible data before explicit healing repaired a local object. RabbitMQ had no confirmed return under its original identity when the record ended.

In production, a membership-only check could conceal degraded redundancy, and a healthy surviving broker could conceal a missing member. Check the returning node’s stable identity, membership, listeners and local data state. Distinguish automatic steps from administrator repairs and retest the complete return sequence after a fix.
