A Node Returned, but Its Cluster State Did Not Fully Return

Hostname identity and local data resynchronization produced two different recovery failures.

A node reappeared after restart, but that did not mean its cluster state had recovered. One broker returned under a changed hostname. An object-store node rejoined before its local shard was restored. Membership, identity and data health needed separate checks.

Reboot changed the broker identity

DHCP reset a RabbitMQ node’s hostname at boot. The broker started under a new, unclustered identity, and rejoin was not confirmed before the trace ended. Other members remained healthy. (commands.)

A hostname used as part of the cluster identity must survive the network configuration applied at boot.

Membership recovery preceded shard recovery

An object-store node rejoined automatically, but its local shard stayed unhealthy until an explicit healing command changed its status. Membership recovery worked; automatic local resynchronization was not established. (commands.)

A node appearing in the cluster does not by itself establish that its local data is fully synchronized.

Recovery claims need a level

Neither case supports a blanket statement of unrecoverable data loss. The first lacks confirmed rejoin at the end of the trace; the second demonstrates repair after manual intervention. The narrower useful claims concern persistent identity and whether local resynchronization was automatic.

What should an administrator check?

A recovery check should reconcile the expected node identity, membership, application behavior and local data health. A green endpoint on a peer can coexist with a missing member or incomplete shard. Recording those levels separately makes both the success and the remaining repair visible.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines.
