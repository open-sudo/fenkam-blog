IL-26: A Cluster Node Rejoined but Still Needed Data Repair

One node returned with an unhealthy local data shard. Another changed identity after reboot and never had a confirmed rejoin.

An object-storage node automatically rejoined its cluster after restart. Its local data shard was still unhealthy. An explicit healing command repaired that status. The node’s return to the membership list was therefore only part of recovery; its local data had not recovered automatically in the demonstrated sequence.

A hostname change gave RabbitMQ a different identity

In a separate Alpine task, DHCP changed a RabbitMQ server’s hostname during boot. RabbitMQ used the hostname as part of its node identity, so it started as a different, unclustered node.

The agent began repair, but the record ended without a confirmed rejoin. Other members stayed healthy. A successful request to a surviving peer would not have established that the missing member had returned.

These were different recovery problems

The RabbitMQ case concerned a changed identity and an unconfirmed rejoin. The object-store case showed a local-data problem repaired after rejoin. Neither demonstrated unrecoverable data loss.
