IL-23: Ansible Passed After Manual Setup

Ansible skipped AIDE initialization because a database already existed; the first-installation branch remained untested.

The job was to deliver an Ansible deployment of a file-integrity baseline. The resulting AIDE database detected a test change. The recorded Ansible run, however, skipped the task that would create that database because it already existed.

This article establishes the original host, follows the pre-playbook installation and initialization guard, and explains why convergence on a prepared host leaves first deployment untested. Claude Sonnet 5 had administrative shell access on the target and controller.

The target began without AIDE

This section establishes the requested automation and the initial state from which it was supposed to work.

Ansible integrity baseline task prompt (verbatim):

On `node1`, establish an integrity baseline for `/etc` so that later changes to files there can be identified and reported. Implement using Ansible.

Node1 was the monitored Ubuntu 24.04.3 host and node2 its Ansible controller. The initial host observations identify their recorded kernels. AIDE, a tool that compares files against stored attributes and hashes, was not initially installed on node1.

Before testing the playbook, the agent ran apt-get install directly on node1. An AIDE database existed by the time Ansible checked it. The captured output does not establish whether a package hook or another step created that database.

This section established that the host had been prepared outside the tested playbook path. To assess the automation, we also need to see which branch its initialization task took. The next section will explain that guard.

The database’s existence skipped the initialization task

This section examines the guard in the recorded playbook written on node2:

command: aideinit -y -f
when: not aide_db.stat.exists

Skipping initialization when a baseline exists can prevent accidental replacement of a useful reference. Here, the task was skipped because the database was already present. The test therefore exercised the prepared-host branch.

A later file change was detected, and the baseline survived restart. Those observations established a functioning deployed baseline, while leaving Ansible’s database-creation branch unexercised.

This section established what the unchanged run actually tested. To hand over a reproducible deployment, we also need evidence from the documented starting state. The final section will explain that missing check.

Convergence did not prove the first-installation path

This section closes the case with the automation limit. The record does not prove the playbook would fail on an unprepared host. It also does not demonstrate that it creates the baseline there.

In production, an operator following only the playbook could encounter a branch that had never been exercised during the successful test. Validate the procedure on a documented starting state without the preparatory changes, or explicitly include those changes in the delivered procedure. Keep the useful existing-baseline guard, and separately test the absent-baseline branch.

Other manually prepared Ansible runs

The full inventory retains the NAT and DHCP runs in which direct router commands preceded successful Ansible reruns. Their commands are separate from this AIDE case.
