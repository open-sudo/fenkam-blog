IL-21: Ansible Reruns Passed After Manual Repairs to the Host

An unchanged Ansible run showed that a repaired host matched the playbook. It did not prove the playbook could reproduce the manual repairs.

The revised Ansible playbook reported no changes. By then, the agent had already repaired the host manually. That can be a truthful result: the host now matches the playbook. It does not prove that the retained automation can create that state from the intended starting point.

Imagine checking a flat-pack assembly guide against a chair a carpenter has already finished. Every part is in the right place, so the inspection passes. That does not show the instructions can build the chair from the box. An unchanged automation run after manual repairs leaves the same question about the retained playbook.

The baseline existed before automation reached initialization

AIDE and its baseline were prepared manually before Ansible ran. The playbook’s initialization task skipped the already-existing state. The successful rerun therefore did not demonstrate first-time baseline creation. (commands.)

An integrity-monitoring task installed and initialized material directly, then ran a playbook whose guard skipped initialization.

A direct router repair supplied the intended NAT state

After failed router playbook runs, a debug script applied NAT directly. The next playbook run reported no changes. That verified the repaired state, rather than the complete path needed to create it. (commands.)

When a debug script creates the working configuration after failed automation, the next unchanged playbook run can be genuine without proving the provisioning path.

Corrected syntax converged on manually configured DHCP

Two DHCP tasks reached working router configuration through direct CLI sessions after automation failures. Revised playbooks then reported no changes. Whether they could build the same configuration from the intended baseline remained untested. (first trace; second trace.)

Both DHCP cases reached working router state through direct CLI sessions before the revised automation reported no changes.

What should an administrator check?

The fair test uses a documented baseline on which the manually supplied state is absent, or captures a complete retained bundle that explicitly includes the preparation step. Idempotence on an already-configured host and rebuildability from the intended starting point are related but different guarantees. The record does not establish the playbooks must fail that missing test.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines. The source extract includes all 4 cases grouped under this topic, their commands and assessment references, and the limits of each finding. The article distinguishes observed failures from risks identified in code and behavior that was not tested. No production attack is claimed. Original records are available in InfraSet.
