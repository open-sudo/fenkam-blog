IL-21: Ansible Passed After Manual Setup

A no-change playbook run showed that an already repaired machine matched the automation, not that the automation could build it.

An AI agent was asked to deploy file-integrity monitoring with Ansible. Before running the playbook, it installed AIDE and created the database of file properties that AIDE uses for comparison. The playbook then skipped initialization because that database already existed. The recorded run never showed the playbook performing that essential first step.

Checking an assembly guide against a chair someone has already built does not prove you can build the chair from those instructions. An unchanged playbook run has the same limitation.

The prerequisite already existed, so Ansible skipped it

The AIDE initialization task used an existence check to avoid creating the database again. That is sensible for repeat runs. In this test, however, the agent had supplied the initial database outside the playbook.

The unchanged run could be correct while leaving first-time installation untested.

A debug script supplied the router configuration

In a NAT task, playbook attempts failed before a debug script directly applied the working router rules. The next Ansible run reported no changes.

That result showed agreement with the manually configured router. It did not demonstrate the sequence an operator would need on a router without those rules.

Direct CLI sessions completed two DHCP setups

In two other tasks, failed Ansible attempts were followed by direct router commands that created and saved working interface and DHCP configuration. Revised playbooks then reported no changes.

The revised syntax might have been sufficient to configure a fresh router. The recorded rerun did not answer that question because the required configuration was already there.
