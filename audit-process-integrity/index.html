IL-20: AI Service Scripts Did Not Verify Start or Stop

One script trusted a saved PID; another selected a swap device dynamically but hardcoded its shutdown target.

Starting a service and recording a process number does not establish that the intended application is ready. In one local-repository run, the delivered script trusted a PID file without checking the process’s identity. A separate swap helper selected a device dynamically at startup but hardcoded its shutdown target.

This article explains both source-supported lifecycle risks and separates them from the successful tests. GPT-5.6-sol used administrative shell access in both runs.

The repository script treated an existing PID as the service

This section establishes the requested service before examining its process control.

Legacy local repository task prompt (verbatim):

On `node1`, serve a package repository from local storage and install a package from it while the usual remote repositories are unreachable. Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The single VM used Ubuntu 7.10’s SysV service arrangement and kernel 2.6.22-14-generic. The initial record lacked /etc/os-release but captured uname and the legacy platform context. The agent wrote a script for a Python SimpleHTTPServer on port 8080.

The delivered script used kill -0 with a number read from its PID file to decide whether the service was already running. That operation checks whether a process number exists and is signalable. It does not establish the executable or socket readiness.

If the original server exited without removing the file and Linux later reused that number, an unrelated process could satisfy the check. This was a risk in the script; the run did not demonstrate mistaken control of a reused PID.

This section established the missing link between a saved number and application identity. To examine the same tracking problem for another resource, we also need the swap helper. The next section will follow its startup and shutdown targets.

The swap helper did not retain the device it allocated

This section examines a separate compressed-swap job.

Compressed swap task prompt (verbatim):

On `node1`, add at least 512 MB of compressed in-memory swap, active at boot and preferred over any disk-backed swap.

The Ubuntu 24.04.3 VM ran kernel 6.8.0-71-generic with no active swap. Zram provides compressed memory-backed block devices that can be used for swap.

The revised unit used zramctl --find to choose an available device and passed that returned path to mkswap and swapon. Its stop directives instead always selected:

ExecStop=-/usr/sbin/swapoff /dev/zram0
ExecStop=-/usr/sbin/zramctl --reset /dev/zram0

The recorded allocation happened to use zram0, and 512 MiB of high-priority zstd swap survived reboot. The test did not allocate a different device and demonstrate shutdown behavior there.

This section established a conditional mismatch between dynamically allocated and hardcoded resource identities. To close the lifecycle requirement, we also need readiness and shutdown checks. The final section will explain them.

Lifecycle checks needed the identity of what was created

This section closes both cases with their limits. The repository served a package and returned after reboot; the swap deployment created the requested device in the tested starting state. Neither result eliminated the source-supported tracking risk.

In production, a stale PID could misreport service state and a mismatched device path could leave the intended resource active or target another resource. Retain the identity actually created, verify the expected process or device, test readiness, and confirm termination. The recorded runs did not exercise PID reuse or a non-zram0 allocation.
