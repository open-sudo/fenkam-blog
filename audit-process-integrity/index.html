The PID Existed. Was It the Right Service?

Generated control scripts confused a process number, a running service and ownership of the resource to stop.

An init script found a live PID and called the service running. Another start script reported success before the application bound its port. Process existence, process identity and readiness are different things. The control logic needs to know which one it has actually established.

A live PID stood in for service identity

An init script trusted a stored PID and kill -0 without matching the expected application, start identity or listener. The code supported a mistaken-identity risk; the test did not demonstrate every possible PID-reuse failure. (commands.)

A PID file and a successful existence check do not establish the expected executable, process start identity or ownership of the listening socket.

The start path reported success before binding

Two daemon start paths recorded a PID before binding the HTTP socket. A successful parent exit or existing PID file could therefore precede a serving child. One runtime directory was writable by the serving account as well. (first trace; second trace.)

A daemonizing parent can exit successfully before its child has acquired the application port.

The stop path forgot a process that could still be alive

Two stop paths waited only a bounded interval, then deleted the PID file and reported stopped without failing if the process still lived. The supervisor could forget a process it had not actually stopped. (first trace; second trace.)

A bounded wait is useful only if its timeout has an explicit result.

Start and stop disagreed about the allocated device

A zram start command selected an available device dynamically, while stop hardcoded /dev/zram0. The helper did not retain the chosen device identity, so allocation and cleanup could target different resources. (commands.)

The zram case is a related ownership problem outside ordinary daemon PIDs.

What should an administrator check?

A dependable lifecycle ties status, readiness and cleanup to the same owned process or resource. That can involve a service manager, process start identity and listener checks, or a stored allocation identifier. The relevant failure mode is mistaken identity, not a claim that all PID files or all dynamically allocated devices are unsafe.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines. The source extract includes all 6 cases grouped under this topic, their commands and assessment references, and the limits of each finding. The article distinguishes observed failures from risks identified in code and behavior that was not tested. No production attack is claimed. Original records are available in InfraSet.
