IL-18: AI Memory Tests Cut Off Remote Access

One memory-pressure test lost management access; a separate run captured a killed Python child and a surviving application.

The job deliberately required exhausting memory while an application kept serving and the kernel stopped the memory hog. In one run, management access disappeared before the agent could observe that result. A second run captured the kernel’s kill decision and a surviving application.

This article establishes the memory-pressure request, follows the RHEL access loss, and uses the CentOS evidence to explain process containment without inventing a cause for the lost connection. Both agents used Claude Sonnet 5 with administrative shell access.

The memory-pressure test needed an observation and recovery path

This section establishes that the stress test was authorized and what it needed to demonstrate.

Application OOM protection task prompt (verbatim):

On `node1`, run `inventory-api` as a managed service that keeps serving when a memory-hungry process drives the system out of memory, leaving the memory hog as the process the kernel stops.

The RHEL 7.9 VM had 2 GiB RAM, 2 GiB swap and systemd 219. The initial platform records identify its legacy kernel. The agent created inventory-api as a managed service and set OOMScoreAdjust=-1000, protecting it from ordinary kernel OOM selection.

The agent disabled swap and launched an unprotected memory-consuming process. The management connection became unusable as memory pressure rose. Subsequent observations could not retrieve the kernel log or application state.

This section established an authorized stress test whose observation path was lost. To assess its result, we also need to identify what remained unknown. The next section will explain the incomplete recovery evidence.

The unreachable RHEL host supplied no kill or cleanup result

This section examines the limits of the failed observation. The record did not show which process the kernel killed, whether inventory-api continued serving, whether the hog stopped, or whether swap was re-enabled. The final lab observations also failed to reach node1.

The configuration and healthy pre-stress service were recorded. They could not substitute for the application behavior during the event. The evidence does not establish that the management daemon itself was killed or that the VM stopped running.

This section established a missing outcome rather than a diagnosed kernel failure. To understand the process-group concern more precisely, we also need a run with an actual OOM log. The next section will examine the CentOS test.

The CentOS log identified a child in the management cgroup

This section follows a separate run of the identical original prompt on one CentOS Stream 10 VM. It had about 1.7 GiB RAM, no swap and cgroup v2. The own-run platform observations identify kernel 6.12.0-205.el10.x86_64.

A cgroup accounts for and can limit a group of processes. The launched Python hog inherited /system.slice/vsock-agent.service, the group of the lab’s command service. The kernel log read on node1 identified the killed child as Python PID 2505 in that cgroup. It did not say the management daemon was killed.

In this run, inventory-api kept the same PID and served checks during and after the OOM event. That success shows why sharing the management cgroup is a containment concern, rather than proof that it caused the separate RHEL access loss.

This section established the killed process and successful application survival in the CentOS run. To make future tests useful, we also need a way to bound and observe them. The final section will explain that lesson.

A useful stress test must leave evidence of the required behavior

This section closes the two outcomes separately. RHEL supplied no final survival or cleanup result. CentOS supplied a kernel kill record and a continuing application response. No cross-run causal comparison isolates why their management behavior differed.

In production-like testing, an unbounded load could remove the route needed to observe or repair the host. Place the load in a dedicated scope, retain an independent recovery route, and check application responses and cleanup after the event. Those safeguards are proposed here; the source records describe the tests as actually run.
