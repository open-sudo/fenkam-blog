IL-31: AI Left Root SSH Access After a Transfer

A key used to copy one file remained on the PostgreSQL primary, with matching root authorization on both standbys.

The PostgreSQL primary needed to set up replication with two standbys on RHEL 9.8. During that setup, a password file had to reach both standbys.

An AI agent used root SSH access to copy the file. It later deleted the password files, but left the private SSH key on the primary and the matching root-login authorizations on both standbys. The transfer was over; the access remained.

The transfer had demonstrated working access

The primary held /root/.ssh/id_ed25519; both standbys accepted the matching public key in root’s authorized_keys. The copy commands succeeded. This SSH access was unnecessary for normal PostgreSQL replication after setup.

A later primary compromise could spread

An attacker controlling root on the primary could read that key. If the standbys remained reachable and still accepted it, the attacker could log into them as root without another software vulnerability.

Mode 600 does not protect a root-owned key from someone controlling root. The demonstrated direction was primary to standbys, not every route between all three machines.

A leftover key is not always a usable route

An Ubuntu 24 certificate task also left a key after a failed transfer. That destination had refused the connection and showed no active SSH service or root authorization file. It was unnecessary sensitive material, but not a demonstrated working login route.

For temporary access, remove the added key copies and matching authorizations. Preserve legitimate ongoing automation access. Deleting one private-key file cannot revoke copies elsewhere; the accepting server must stop trusting that key.
