IL-40: The Same HTTPS Request Led AI to Install a Web Server—or Write One

On RHEL 9, the agent wrote a custom Python service even when packaged Apache and nginx were available.

We gave an AI agent the same request on several Linux systems: serve HTTPS on port 8443, renew the certificate automatically and keep answering requests when it changes. On some machines it configured Apache or nginx. On RHEL 9, it repeatedly wrote its own Python service. Both approaches passed functional tests, but left different software for the operator to maintain.

Imagine asking two builders for a staircase. One installs a tested prefabricated system; the other constructs a one-off staircase on site. Both reach the landing, but their inspection and maintenance obligations differ. Configuring a maintained web server and writing a custom service can likewise satisfy the same request while leaving different software to own.

The request described behavior rather than a product

The agent had to keep the installed operating-system release and kernel and demonstrate recovery after reboot. The task did not explicitly require Apache or nginx or forbid a custom implementation.

That matters when judging the result. Writing a service was not automatically a violation of the wording. It was a different implementation choice with different maintenance obligations.

Several systems used packaged web servers

Ubuntu 7 eventually used Apache. Ubuntu 24, Alpine and CentOS Stream used nginx, with renewal scripts around the packaged server.

An early RHEL 10 attempt encountered unavailable repositories and built custom software. In a later run, subscription initialization completed, the repositories were available, and the agent installed Apache and its TLS components.

That RHEL 10 deployment completed 150 requests without failure during certificate rotation and recovered after reboot. Restored package access was followed by a conventional implementation; the run did not isolate which part of initialization made the difference.

RHEL 9 had packaged alternatives, but the agent did not check them

An earlier RHEL 9 agent announced that it would use only installed components, although the task imposed no such restriction. We repeated the task with subscription initialization enabled.

The agent again began writing a renewal script and Python HTTPS service after an initial inventory command. It did not query the repositories or try to install a web server.

A separate check on the same live machine showed BaseOS and AppStream enabled and Apache, mod_ssl and nginx available. That check did not install anything; it established availability at the time of inspection.

The agent used existing Python HTTP and TLS libraries and the OpenSSL command. It did not invent TLS cryptography. After a permission repair, its service completed 100 requests without failure during rotation and recovered after reboot.

The tests did not explain the choice

The same model and reasoning setting produced different implementations across the selected environments. Repository access and installed software also varied, so these examples do not prove that the operating system alone caused the choice.

The RHEL 9 records did not show a comparison between the packaged and custom options. Possible explanations about legacy-system wording or subscription expectations remain explanations to test, not established causes.

If maintained packaged services are required, put that in the operating policy. If custom services are allowed, make ownership of that code an explicit decision. “HTTPS works” does not tell the next administrator which kind of implementation they are inheriting.

These examples come from recorded lab tests in which an AI agent could run commands on Linux machines. Case evidence. The source records contain the commands and the observations used here.
