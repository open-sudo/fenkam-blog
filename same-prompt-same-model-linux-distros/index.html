IL-42: AI Wrote an HTTPS Server Despite Available Packages

On one RHEL 9.8 VM, an agent wrote a Python HTTPS service. Its first certificate rotation failed 78 of 80 requests before a permissions fix.

The job in this lab test was to add HTTPS to an existing Linux virtual machine. The service needed to listen on port 8443, renew its certificate before expiry, and keep answering requests during renewal. The machine, OS and kernel had to stay. The open decision was the web-server software: install Apache or nginx, or write a new HTTPS program.

The AI agent used GPT-5.6-sol and could run shell commands on the VM. It wrote a Python HTTPS program. The evidence links in this article lead to its saved commands and their output.

This article first establishes the host and software options, then follows a failed certificate renewal and its repair. The final section explains what maintaining the custom Python program would mean in production.

The starting host and HTTPS requirements

This section establishes what the agent was asked to do and what was already running on the machine.

The agent received this task prompt (verbatim):

On `node1`, serve HTTPS on port 8443 with a certificate that is renewed automatically before it expires, and have the service pick up each new certificate while it keeps answering requests. Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The machine named node1 was the only VM in this test. Its IP address was 10.100.23.10. The agent’s initial host inspection recorded:

  • OS: Red Hat Enterprise Linux 9.8 (Plow).
  • Kernel: 5.14.0-687.20.1.el9_8.x86_64.
  • Services: systemd was PID 1 and managed service startup. SSH was the only service listening for TCP connections.
  • Software: Python 3 and OpenSSL were present. Checks for the Apache (httpd) and nginx commands found neither. The exact Python and OpenSSL versions were not recorded.

The prompt required keeping the OS and kernel. The lab also checked whether the finished service came back after reboot.

This section established the existing RHEL 9.8 machine and the requested HTTPS behavior. To provide that service, the agent still had to choose a web-server program. The next section will explain what it wrote and how it scheduled certificate renewal.

The agent wrote a Python HTTPS program

This section explains the program and renewal script the agent put on the RHEL machine. The agent wrote autohttps-server.py without checking repositories or trying to install Apache or nginx.

A separate RHEL 9 package check found Apache 2.4.62 with mod_ssl and nginx 1.20.1 available to install. That check was recorded outside the agent’s command log. The evidence extract identifies it separately, including its command and package releases.

The Python program used existing HTTP and TLS libraries. TLS provides the encrypted connection used by HTTPS. The program ran under a Linux user and group both named autohttps. It read /etc/pki/autohttps/active.pem on every new connection. This file contained both the certificate and its private key. The certificate-renewal diagram calls this combined file a “bundle.” Reading it on each new connection let the program use a replacement certificate without restarting.

A separate script ran as root and generated certificates valid for seven days. These were self-signed: the script signed each certificate with its own private key. A systemd timer scheduled expiry checks every six hours; renewal replaced the file when fewer than three days remained. The diagram calls this replacement “certificate rotation.” Commands that created the program and renewal timer.

This section explained how the Python program reads its certificate file and how renewal replaces that file. To keep HTTPS available during renewal, the program also needed permission to read every replacement. The next section will follow the first renewal test and explain why the replacement file caused requests to fail.

Certificate renewal broke the Python HTTPS service

The previous section described a program that reads its certificate file for every connection. This section examines what happened when renewal replaced that file while requests were being sent.

The initial file was owned by root and belonged to the autohttps group. Its mode, 0640, allowed root to read and write it and the group to read it. After correcting the parent directory’s permissions too, the agent obtained a successful HTTPS response and verified TLS connection.

To test renewal without waiting days, the agent temporarily widened the script’s “renew before expiry” window. That made the current certificate due for renewal immediately. The agent started renewal while sending HTTPS requests from node1 to its own IP address.

The renewal script created the replacement file with mode 0600, giving only root access. Moving the new file into place did not preserve the old file’s permissions. During this test, 78 of 80 requests failed. The agent then checked whether the service account could read the replacement file.

The agent ran this recorded command as root on node1. It asks OpenSSL to read the certificate as the Linux user autohttps:

runuser -u autohttps -- openssl x509 -in /etc/pki/autohttps/active.pem -noout -serial

The recorded error output contains Permission denied. This confirmed that the service account could not read the replacement file.

Renewal triggered the failure by replacing the file. The script’s mode 0600 removed the group read access the running program needed. Without the certificate file, the program could not complete the TLS handshake, which sets up the encrypted connection.

This section traced the failed requests to a replacement certificate file that autohttps could not read. To restore HTTPS and make later renewals work, the agent needed to fix the current file and the script that created replacements. The next section will show that repair and the checks used to verify it.

The agent repaired renewal and tested again

This section follows the repair to the unreadable certificate file and renewal script, then checks whether HTTPS kept working when renewal was repeated.

The agent changed the renewal script to create mode 0640 files and fixed the current file’s permissions. The agent then repeated renewal while sending requests from node1 to its own HTTPS service. The recorded request summary was:

requests=100 failures=0

All 100 requests completed successfully. The certificate presented over HTTPS had a new serial number matching the replacement file, confirming that the program had loaded the new certificate.

The repeated requests used curl -k, which skips certificate verification. A separate request used --cacert with the locally generated certificate file to check a verified connection.

After reboot, the service, timer, firewall rule and HTTPS response recovered, with the original OS and kernel intact. A changed Linux boot ID confirmed that the VM had rebooted. These were short local checks of renewal and restart behavior.

This section showed the repaired Python service passing the renewal and reboot checks. To operate it beyond the lab, someone would also need to maintain the Python code and renewal script. The final section will explain that responsibility and how an uncaught renewal defect could affect production.

The Python program became a maintenance responsibility

With the permission defect repaired, this section considers the ongoing work created by deploying a custom Python HTTPS program. The failed renewal shows how a bug in its renewal script can stop clients reaching the service.

The lab caught and fixed the defect. In production, the same defect could leave an endpoint working until a later scheduled renewal replaced its certificate file. New clients would then fail to establish HTTPS connections even though the new certificate had not expired. Checking only the initial installation would miss that failure.

Existing Python and OpenSSL libraries still handled HTTP, TLS and cryptography. The additional responsibility was maintaining the custom code that answered requests and loaded certificates, together with its renewal script. Apache and nginx also need correct renewal configuration; this implementation added the HTTPS program itself to the code someone must review, test and support.

The quoted prompt did not name a web-server program. If the expected result is an Apache or nginx deployment, name that software in the request. If a new Python service is acceptable, assign its maintainer. Test a real certificate replacement, then check that the service account can read the new file and HTTPS remains available.

Other runs of the same HTTPS request

Other runs used Apache on Ubuntu 7 and RHEL 10, and nginx on Ubuntu 24, Alpine and CentOS Stream 10. The RHEL 10 Apache run completed 150 requests during renewal without failure. These runs show different software implementations; they do not establish why the agent chose differently.
