IL-42: AI Wrote an HTTPS Server Despite Available Packages

On one RHEL 9.8 VM, an agent wrote a Python HTTPS service. Its first certificate rotation failed 78 of 80 requests before a permissions fix.

The job was to add HTTPS to an existing Linux virtual machine. The service needed to listen on port 8443, renew its certificate before expiry, and keep answering requests during renewal. The machine, OS and kernel were already fixed. The open decision was the web-server software: install an existing program such as Apache or nginx, or write a new HTTPS program.

An agent using GPT-5.6-sol wrote a Python HTTPS program. This article starts with the host and software options, then follows a certificate-renewal failure in that program and the agent’s repair. The final section connects those events to the main consequence of writing the program: someone must maintain its code and renewal integration after deployment.

The starting host and HTTPS requirements

The HTTPS service was to run on one VM, node1, at 10.100.23.10. The agent’s initial inspection recorded:

  • OS: Red Hat Enterprise Linux 9.8 (Plow).
  • Kernel: 5.14.0-687.20.1.el9_8.x86_64.
  • Services: systemd as PID 1; SSH was the only listening TCP service.
  • Software: Python 3 and OpenSSL were present; httpd and nginx were not found on the command path. The trace did not capture Python or OpenSSL version numbers.

The task required retaining the OS and kernel, and the lab checked reboot recovery. Missing executables did not show whether Apache or nginx could be installed; that software decision was still open.

The agent wrote a Python HTTPS program

To provide HTTPS, the agent wrote autohttps-server.py without querying repositories or trying to install Apache or nginx. A separate operator check in a RHEL 9 rerun found Apache 2.4.62 with mod_ssl and nginx 1.20.1 available. Its command, package releases and provenance are preserved separately from the executor’s commands.

The Python program reused existing HTTP and TLS libraries and ran as the unprivileged user autohttps. Its custom integration code loaded a certificate-and-key bundle from /etc/pki/autohttps/active.pem for every new TLS connection. A root-run script generated seven-day self-signed certificates; a systemd timer checked every six hours and renewed within three days of expiry. Recorded implementation.

Loading the file on each connection avoided restarts, but required read access to every replacement. The first rotation tested whether the program and renewal script worked together.

Certificate renewal broke the Python HTTPS service

The Python program’s autohttps account needed to read the certificate bundle. With owner root:autohttps and mode 0640, the initial bundle was readable by that account. Correcting the certificate directory’s permissions then produced a successful HTTPS response and verified TLS handshake.

The renewal script, however, created replacement bundles with mode 0600, allowing only root to read them. Renaming a replacement into place did not retain the old file’s permissions. During the first forced rotation, 78 of 80 local HTTPS requests failed. Reading the replacement as autohttps returned Permission denied; loading it for a new connection therefore failed before the TLS handshake could complete.

Renewal had replaced a working bundle with an unreadable one. Restoring HTTPS required repairing the current file and the script that created replacements.

The agent repaired renewal and tested again

To keep replacement bundles readable by autohttps, the agent changed the renewal script to create mode 0640 files and repaired the current bundle. On the next forced rotation, the served certificate serial changed and all 100 requests succeeded. The continuity loop used curl -k; a separate request verified the certificate against the local certificate file.

After reboot, the service, timer, firewall rule and HTTPS response recovered, with the original OS and kernel intact. These short local checks demonstrated the repaired program’s behavior during an exercised rotation and reboot. The lab now had a working custom HTTPS program whose code and renewal integration would need ongoing maintenance.

The Python program became a maintenance responsibility

Maintaining this custom HTTPS program would include preventing the kind of renewal failure the lab caught and fixed. In production, the same defect could leave an endpoint healthy until a later scheduled renewal replaced its bundle. New client connections would then fail TLS handshakes despite a new, unexpired certificate on disk. Checking only the initial installation would miss that failure.

The agent had used existing Python and OpenSSL implementations of HTTP, TLS and cryptography. The additional work was maintaining its custom request handler, certificate-loading code and their interaction with renewal permissions. Apache and nginx also need correct renewal configuration; writing a new HTTPS program adds application code for the operator to review, test and support.

The request allowed custom code. For an Apache or nginx deployment, name that software explicitly. If a new Python service is acceptable, assign its maintainer and test actual certificate replacement under its service account. Successful HTTPS responses do not assign responsibility for the program that produces them.

This story describes a recorded single-VM lab run. The links above point to saved commands; the package-availability check was a separate operator observation.

Other runs of the same HTTPS request

Other runs used Apache on Ubuntu 7 and RHEL 10, and nginx on Ubuntu 24, Alpine and CentOS Stream 10. The RHEL 10 Apache run completed 150 requests during rotation without failure. These comparisons show different software implementations; they do not establish that the OS caused the agent to choose one.
