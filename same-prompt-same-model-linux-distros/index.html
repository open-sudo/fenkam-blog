IL-40: AI Wrote an HTTPS Server Despite Available Packages

On RHEL 9, the agent wrote a Python HTTPS service without checking the available Apache and nginx packages.

We asked the same AI model to serve HTTPS on port 8443, renew certificates automatically and keep answering requests during renewal. It configured Apache or nginx on several systems. On RHEL 9, it repeatedly wrote a custom Python service instead.

Apache and nginx were available on RHEL 9

Ubuntu 7 used Apache; Ubuntu 24, Alpine and CentOS Stream used nginx. An early RHEL 10 attempt wrote custom software when repositories were unavailable. A later RHEL 10 run had repository access and installed Apache.

On RHEL 9, the agent did not query repositories or try a package installation. A separate check on the same live machine confirmed Apache, mod_ssl and nginx were available.

The custom server passed the tests

The RHEL 9 program used Python’s existing HTTP and TLS libraries, not newly written cryptography. After a permission repair, it completed 100 requests during certificate rotation without failure and recovered after reboot. The Apache deployment on RHEL 10 completed 150 requests and recovered too.

The operator inherited new server code

The request specified behavior, not a product, so a custom server did not automatically violate it. It did leave the operator responsible for new service code instead of a maintained web-server package.

These runs do not prove the operating system caused the choice. They show why a requirement to use approved packaged services should be explicit.

Documentation

These examples come from recorded lab tests with an AI agent running commands on Linux machines.
