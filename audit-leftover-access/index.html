IL-4: AI Left Temporary Login Access Behind

Access created for a transfer, a failed experiment or a login test sometimes remained after its purpose had ended.

I wanted a database import completed on Ubuntu 16.04. During setup, a file holding database credentials needed to move between two servers. That was a one-time transfer; normal database operation did not need to keep the new SSH access.

An AI agent created the SSH access and delivered the file. It left the matching login authorization behind. Other tasks similarly retained accounts or keys from abandoned approaches and verification tests.

Abandoned approaches left credentials on disk

An attempted certificate transfer failed, but its SSH credentials remained. In another deployment, the agent replaced an Ansible login credential without removing the original.

A failed connection is not proof that an attacker could use that credential. The destination might reject it or have no SSH service. It does mean cleanup must account for an approach that was abandoned before it worked.

Login tests created access of their own

Testing SSH certificates required temporary identities and keys. Some tests left a root-login credential, a private-key copy or a matching authorization entry behind.

An administrator needs to know which of these were test-only and which are part of normal operation. Their filenames alone may not explain the difference.

Some changes spread access further

One task copied a shared root private key to several machines. Compromising any machine that holds a usable copy could then expose that credential. A separate database experiment left a remote-root grant that accepted connections from a broad range of source hosts.

Whether either route can actually be used depends on the remaining credentials, server policy and network access.
