Temporary Access Became Part of the Deployment

One-time transfers, abandoned experiments and verification accounts left credentials or grants behind.

An agent needed administrative access to move a file between servers. The transfer ended, but the access did not. Other runs left credentials from failed experiments or test logins behind. A later compromise could make some of that access useful to an attacker, depending on which keys remained and which servers still accepted them.

A completed transfer left its authorization behind

One database transfer left standing SSH authorization after the file had arrived. A separate task retained temporary root-transfer access. The question at handover was whether that continuing access still had a job. (first trace; second trace.)

A failed approach left credentials without a continuing job

A failed certificate-transfer attempt left unused SSH credentials. Another deployment replaced a failed Ansible credential but retained the original. Failed access is not proof of a working attack path, but the abandoned credential still needs a disposition. (first trace; second trace.)

An abandoned connection attempt can leave private keys and authorizations on disk even when it never established a working session.

Verification introduced another identity

Host-certificate verification left a root-login test credential and a private-key copy. Another certificate test retained its test key and authorization. Checking that a new login method works creates cleanup work of its own. (first trace; second trace.)

Testing certificate-based or remote login can create a separate credential lifecycle.

Credentials spread beyond the machine that needed them

One task distributed a shared root private key across the topology. A separate abandoned database approach left a wildcard remote-root grant. The first increases where a credential can be obtained; the second broadens where authentication may be attempted. (first trace; second trace.)

Copying a private key to every participant increases the number of places from which it might later be obtained.

What should an administrator check?

Ongoing automation may legitimately require access. Temporary transfer access needs an explicit end, while continuing access needs an owner and a justified scope. Removing unfamiliar keys indiscriminately could break administration; the useful evidence connects each added credential to its purpose and final disposition.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines.
