IL-37: The Same AI Task Left Servers With Different Packages and Repairs

Three RHEL 10 repository setups worked, but one upgraded core libraries, one rolled packages back and one avoided the repair entirely.

The request was to serve a package repository from local storage and prove an installation still worked when remote repositories were unavailable. In three RHEL 10 runs, the agents reached that result through different changes to the host. The servers could all be called “RHEL 10 with the original kernel,” while needing different maintenance afterward.

Imagine a delivery company asking three garages for the same van repair. One fits the standard part, another replaces the wiring, and a third changes the engine controls. All three vans drive away, but they no longer share the same maintenance needs. Successful AI deployments can leave that kind of hidden variation across a server fleet.

One demonstration broke package management and required core-library repair

The agent chose to build an RPM for the demonstration. Installing its build prerequisites added 33 packages and upgraded nine. A new RPM cryptography component needed OpenSSL symbols missing from the machine, after which RPM and DNF stopped working.

The agent recovered by extracting newer OpenSSL libraries from a package and placing them in the live system. A later package transaction, retried with --nogpgcheck, reconciled the repair and upgraded OpenSSL, FIPS-provider packages and crypto policies.

The repository eventually worked, the machine rebooted, and dnf check passed. It was not left with the manually copied libraries unaccounted for. It was left with wider package changes than a repository demonstration alone would suggest.

Another run restored a compatible older RPM stack instead of taking the OpenSSL-upgrade route. A third previewed its prerequisite transaction and served an existing tree package. Its prerequisite transaction installed only two packages, avoiding the build-tools installation and core-library repair.

These were not identical experimental settings

The task text was the same, but the later runs had extra operating-practice instructions about preservation, security, minimal changes and verification. They also used different reasoning settings.

The comparison therefore does not prove that randomness or a particular reasoning setting caused the differences. It does show the different machine states produced by those separate executions.

Other operating systems left different changes to maintain

RHEL 9 used repository tools, Apache and an existing tree package. AlmaLinux used tree too and removed extra downloaded dependency packages before finishing.

CentOS Stream left ordinary remote repositories moved aside. RHEL 7 installed repository tools from CentOS Vault with signature checking bypassed and retained a local source with checking disabled.

Alpine created a signed APK repository, served it through lighttpd and restored its temporary remote-repository block. Ubuntu built a demonstration DEB but left an APT proxy that continued blocking ordinary HTTP repositories.

Different package managers are expected across distributions. Unexpected security exceptions, blocked update sources and core-library changes are the differences an operator needs documented.

The difference matters when the next update arrives

Consider an administrator trying to patch a cryptographic library. On one server the normal update sources work. On another they are disabled. A third has already received a library upgrade during an unrelated task.

The same update procedure may behave differently on each machine. These are possible maintenance consequences, not a production incident observed in this set of lab runs.

Documentation

Specify the machine you want to inherit

Give the agent approved package sources, service choices and security requirements, along with the requested behavior. Ask for a record of installed and upgraded packages, repository edits and any repair to core components.

Ansible can capture the result, but separately generated playbooks can still describe different designs. A fleet needs agreed designs and an inventory of the actual state, not just proof that each demonstration worked.

Hosts do not need to be identical across operating systems. Their differences need to be deliberate and visible to the people who will update and repair them.

These examples come from recorded lab tests in which an AI agent could run commands on Linux machines. Case evidence. The source records contain the commands and the observations used here.
