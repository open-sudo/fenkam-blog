IL-39: The Same Task Left Different Server Configurations

Three repository runs on RHEL 10 left different package states, with differences in instructions and test coverage.

The operational job was to install a package from a repository served by the same RHEL machine while ordinary remote sources were unavailable. Three recorded runs achieved a local installation, but they reached that result through different package changes. Those differences determined what the next administrator would maintain.

This article establishes the common task and each starting host, follows the two repair paths and the smaller installation, and explains why the runs cannot isolate a cause for the variation. All three agents used GPT-5.6-sol with administrative shell access.

Three separate RHEL hosts received the same task text

This section establishes what the runs had in common before comparing their choices.

Local repository task prompt (verbatim):

On `node1`, serve a package repository from local storage and install a package from it while the usual remote repositories are unreachable. Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The identical text appears in the second run’s original prompt and third run’s original prompt. Each run used one RHEL 10.0 VM named node1 on kernel 6.12.0-55.9.1.el10_0.x86_64. The initial inspections recorded DNF and RPM, with 411 installed packages in the first run. They did not establish that every installed package version was identical across all three runs.

The first host, second host and third host were separate lab executions. The third initially had SSH listening and no repository HTTP service. The task left the package and serving program open.

This section established the shared request and the limits of the starting-state comparison. To explain the resulting configuration differences, we also need the package transactions. The next section will follow the build-tools route and its library failure.

Building a demonstration RPM broke the package tools

This section follows the first run’s choice to build a demonstration package. Installing build prerequisites added 33 packages and upgraded nine. The updated rpm-sequoia cryptography library required OpenSSL symbols missing from the installed libraries. RPM, rpmbuild and DNF then failed to load.

The agent copied extracted libraries into the running system to regain usable tools, then reconciled the OpenSSL packages with --nogpgcheck. That repair upgraded five packages, including OpenSSL libraries and cryptographic policies. This was a signature-check exception in the repair transaction.

The final package check showed a functioning package manager, OpenSSL libraries 3.5.8 and removal of the manual repair copies. A local package installation and reboot succeeded. The host had a consistent package database, alongside a changed core software stack.

This section established how one demonstration expanded into core-library repair. To assess the available variation, we also need the other two executions. The next section will explain their rollback and smaller prerequisite transaction.

Another run rolled back RPM; a third avoided the build tools

This section compares two further ways of completing the same repository job. The second run encountered the same incompatibility, then extracted an older RPM stack into a temporary directory. It verified package signatures and previewed the downgrade before installing compatible RPM components.

The recorded rollback restored native tools. It did not prove equality with every original package release because a complete baseline version list had not been captured.

The third run chose an existing signed tree RPM and previewed only the repository-metadata tools. Its root-shell preview on node1 returned this recorded transaction summary:

Install  2 Packages

The preview named createrepo_c and createrepo_c-libs. The agent installed them and served tree 2.1.0 from local storage. The final checks showed working package tools, SELinux enforcing, and a restricted service identity after reboot.

This section established three different maintenance outcomes behind a local-installation success. To interpret that comparison, we also need the instruction and verification limits. The final section will explain them.

The records show variation without isolating its cause

This section explains what the three successful demonstrations can support. The later runs also received execution-level instructions about preserving state, limiting changes and checking security. The first two used high reasoning effort; the third used xhigh. These were not controlled trials with every surrounding instruction and setting held constant.

The third run demonstrated remote unavailability by disabling ordinary DNF sources and failing to resolve a remote-only package. It did not capture a transport-layer outage at that moment. The other runs used their own outage demonstrations. Each final result must be interpreted through the checks actually performed.

No production update failure was observed. In production, however, administrators would inherit different RPM or OpenSSL versions and different repair histories. A handover should include added and upgraded packages, repository changes, signature exceptions and the final package-health result. A previewed transaction and an agreed package source can make that review concrete.
