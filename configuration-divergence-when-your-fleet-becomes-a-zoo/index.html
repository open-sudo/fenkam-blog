IL-37: The Same Task Left Different Server Configurations

The same repository demonstration led to core-library upgrades, an older RPM stack, or a much smaller installation.

I wanted a local package repository to keep serving installations while remote repositories were unavailable. I compared three AI executions of that task on RHEL 10.

All reached a working local installation. They left different software changes behind: one went through core-library repairs, another restored an older RPM stack, and a third used a much smaller prerequisite installation.

Three routes to a working repository

One agent built a demonstration RPM. Its prerequisites added 33 packages and upgraded nine, breaking RPM and DNF because a new component needed missing OpenSSL symbols. It repaired the system with newer OpenSSL libraries, then reconciled the packages through a transaction that bypassed signature checks. The reboot and dnf check passed, but cryptographic libraries and policies had changed.

A second run restored a compatible older RPM stack. A third previewed its prerequisite transaction and used an existing tree package for the demonstration. That transaction installed only two packages and avoided the build tools and core-library repair.

The instructions were not identical in every respect

The task text was the same. Later runs also had instructions to preserve existing state, limit changes and verify security, and they used different reasoning settings. The comparison shows the resulting configurations; it does not isolate why the agents chose differently.

Other systems had their own leftovers

RHEL 9 used Apache and an existing tree package. AlmaLinux used tree and removed extra downloaded dependencies. Alpine created a signed APK repository, served it through lighttpd and removed its temporary block on remote repositories.

CentOS Stream left normal remote repositories moved aside. RHEL 7 retained a source with signature checking disabled after installing tools from CentOS Vault. Ubuntu left an APT proxy that still blocked normal HTTP repositories.

Record the changes that affect the next update

Different distributions need different tools. Blocked update sources, signature exceptions and core-library repairs are additional differences an operator needs to know about.

Give the agent approved package sources and service choices. Review installed and upgraded packages, repository edits and repairs—not just whether the demonstration worked. No later production patching failure was observed in these lab runs.
