What 905 AI Sysadmin Runs Left Behind

Most tasks passed. The command logs and final machine checks showed what the success rate left out.

I ran an AI agent 905 times on sysadmin tasks using isolated virtual machines. It passed 837, or 92.5%. A separate review found unnecessary files or changes left behind in 403 runs. A working service and a clean handover were different outcomes.

Each run used Claude Sonnet 5 at medium reasoning effort, with one to four machines and no human intervention. Some machines began clean; others had prepared faults or existing configuration. The tasks covered Linux releases from Ubuntu 16.04 to RHEL 10, as well as VyOS, OPNsense, OpenWrt and SONiC network systems.

The model issued 59,349 commands. Across all 922 attempts, the experiment created 2,355 virtual machines; 17 attempts failed in the surrounding test system and were excluded from the 905 model runs. At peak, 50 VMs ran at once.

Harbor assigned tasks and recorded commands. Antrieb created the isolated machines and networks. The tasks, logs and results are on GitHub and Hugging Face.

1. Most runs passed the requested checks

A pass meant every stated requirement was judged met. A separate AI verifier reviewed the task, network layout, commands, outputs and machine snapshots. Snapshots were taken before preparation, before the agent started and after it finished. They recorded files, packages, services, ports and reboot state.

The report linked each decision to evidence. That makes a result inspectable, though the verifier itself can make mistakes.

2. Command failures varied by system

For the same 29 tasks, commands failed four times as often on RHEL 7.9 as on RHEL 9.8. Network-device command failure rates were closer together: 7.1% on SONiC to 8.0% on VyOS. These comparisons show where the agent struggled; they do not establish why.

Here, a failed command means a non-zero exit status among commands that returned a status. It is not a failed task: an agent can recover from several command errors and finish, or run successful commands against the wrong interface.

The Linux-release chart excludes the file-integrity task, whose long Ubuntu runs are discussed below.

3. Unnecessary files or changes remained in 403 runs

The review counted state introduced by the agent, no longer required by the task and still present at the end. It excluded existing configuration, test-system preparation, required service files and changes the agent cleaned up.

It found leftovers in 403 runs, none in 415, and insufficient information in 87. A run can appear in several categories because it may leave both files and configuration changes.

Seventy-five runs left passwords, keys or certificates. One PostgreSQL run retained its certificate authority’s private signing key at /tmp/pgca/ca.key. Someone able to read that key could issue certificates trusted by the cluster. Other leftovers included test services, packages and settings that the next administrator would need to understand.

4. Multi-machine work took longer

Single-machine work generally took three to four minutes. Networking tasks took six to thirteen minutes, and stateful clusters ten to twenty-five. Replication and failover needed machines to coordinate and demonstrate recovery. One PostgreSQL failover on Ubuntu 24.04 reached the 35-minute time limit.

5. Powerful commands appeared in nearly half the runs

A scan found 1,694 commands in five high-impact classes across 432 of 905 runs: stopping services, force-killing processes, deleting files, flushing network rules and bypassing package checks. The count identifies operations, not whether they were justified.

For example, one command stopped PostgreSQL and removed its data directory before taking a new base backup. That can be appropriate when rebuilding a replica and disastrous on the wrong host. Checking only the command name cannot establish whether its target, timing and purpose are acceptable.

6. Four repository configurations used hostnames that failed

The agent configured external OS repositories in 29 runs. Four used hostnames that failed DNS resolution: three used el9.rabbitmq.com and one used ppa1.rabbitmq.com. The latter had been official, but RabbitMQ had shut it down in November 2025.

The failures caused retries and fallbacks that could change the installed software version. A familiar-looking repository address still needs verification against the publisher’s instructions.

7. Some firewall changes vanished after reboot

Of 237 firewalld cases, 210 retained working configuration after reboot. In 27, or 11.4%, the changes were temporary and disappeared. The prompts required a reboot, though they did not spell out --permanent for every rule.

A service can therefore work during setup and lose required access at the next restart. The useful check is traffic after reboot, before manual repair.

8. A file-integrity check took 32 minutes

The task was to record a baseline for /etc so later file changes could be detected. On Ubuntu 24.04, AIDE scanned nearly 90,000 entries and the task took 32 minutes. Ubuntu 16.04 scanned about 70,000 and took twelve minutes. Other releases generally scanned 30,000–40,000; most finished in about four minutes, while Alpine took six.

On Ubuntu 24.04, a check exceeded the 120-second command limit. The agent relaunched it in the background and waited fixed intervals between status checks. It often slept past completion, repeating that pattern during later operations. The scan size and the agent’s waiting strategy both mattered.

What these results cannot tell us

Every run used one model and reasoning setting. The results do not establish how other models behave. The verifier was also an LLM, and the analysis scripts were written with LLM assistance. Verifier judgments can vary; scripts are repeatable once written but can contain bugs.

A pass rate is useful only with its requirements and evidence. These records let readers inspect both the requested result and the changes outside it.

The lab

The experiment ran in my basement. An HPE ProLiant coordinated four mini PCs that hosted the VMs, connected through an HPE switch and backed by a UPS. USB fans kept the mini PCs cool.
