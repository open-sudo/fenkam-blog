LLM as sysadmin: the illusion of done

59,349 commands. 2,355 VMs. A lot can happen between an agent saying “completed” and a system being genuinely changed.

Give a language model access to a shell and the interface looks familiar immediately. It can inspect files, install packages, restart services, and explain the result in a calm paragraph. That familiarity is useful—and dangerous. The shell is not a simulation. Every command is a small wager against a living system.

We ran a large collection of infrastructure tasks across thousands of virtual machines. The point was not to see whether an LLM could type plausible commands. It was to see what survived contact with the machine: the state before, the commands in between, and the state after.

The transcript is a poor witness

Language models are extraordinarily good at producing a narrative of progress. They can describe what should have happened, infer what probably happened, and compress uncertainty into a sentence that sounds like a conclusion. None of that proves a service is listening on the right interface or that a route persists after reboot.

The most expensive word in an agent transcript is “done.”

Scale changes the shape of failure

At small scale, an occasional hallucinated command looks like a model problem. At scale, the failures become operational categories: a missing call to the execution bridge, an environment that cannot be provisioned, a timeout that leaves no clean handoff, or a verifier that cannot parse what it was given.

Those categories matter because they separate agent behavior from infrastructure availability. If the cluster has reached a daily limit, no amount of better prompting fixes the run. If the agent makes a change but leaves no evidence, the issue is not only execution—it is the contract for proving execution.

Make the machine part of the answer

A reliable loop has at least three voices: the agent’s plan, the executor’s record, and the verifier’s observation. The agent can propose. The executor can report what was actually attempted. The verifier can inspect the resulting state without trusting the story.

That last separation is the important one. Verification should be independent enough to catch a confident lie, including an accidental one. It should look at concrete outcomes: service state, file contents, network behavior, package versions, and persistence across the lifecycle the task cares about.

What “done” should mean

Done is not the end of a conversation. It is a state transition with a receipt. The receipt does not need to be enormous, but it needs to answer the questions a future operator will ask: what changed, where, when, under which authority, and how do we know?

LLMs are useful sysadmins when they are treated as operators inside a system of controls—not as the system of controls themselves. Their range is a force multiplier. Evidence is what keeps that range from becoming a liability.
