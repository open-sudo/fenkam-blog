IL-6: AI Opened More Firewall Access Than Requested

The intended client could connect, but some rules also admitted unnecessary traffic or disrupted existing access.

The upload service was supposed to accept connections from one identified client. The firewall change needed to admit that client while keeping the restriction on everyone else.

An AI agent opened the port to an entire firewall zone. The intended client connected, so the positive test passed. That test said nothing about whether other machines in the zone could connect too.

A named client became a whole zone

An upload-service task and a broker-cluster task both opened ports across a firewall zone rather than limiting access to the expected clients or peers.

A firewall zone groups interfaces or sources under a policy. Allowing a port for the zone can admit more machines than the specific ones named in the request.

Other services and defaults still mattered

An NFSv4 deployment allowed additional RPC services that its requested setup did not need. In an OpenWrt guest-network task, the rules blocked guests from a protected application but still admitted traffic to the gateway’s own administration services.

Troubleshooting temporarily switched filtering off

During an IPsec setup, the agent briefly disabled packet filtering on two gateways. Another investigation left a firewall disabled for about ten minutes before restoring it.

Switching filtering off can help diagnose a connection problem. It also stops enforcing the rules during that interval. No intrusion during these tests was observed.

Some edits removed access that was already needed

Cleanup of a temporary forwarding rule also removed an unrelated WAN forwarding rule. Elsewhere, enabling a firewall before preserving SSH access cut off the agent’s connection to the server.
