AI Firewall Changes Allowed More Traffic Than Requested

Rules were broader than requested, filtering was disabled during diagnosis, and unrelated access changed.

The intended client could connect. That was true in several deployments whose firewall also allowed more traffic than requested. Other agents temporarily disabled filtering or broke existing access while changing rules. A successful connection answers one question; it does not describe the full policy left behind.

Imagine cutting a large opening in a garden fence to let one delivery bicycle through. The bicycle passes, but that test tells you nothing about who else can now enter. A successful connection through a firewall similarly does not show whether the allowed sources, ports and default policy stayed within the intended boundary.

The allowed audience grew

Broker cluster ports were allowed throughout a public firewall zone. An upload-service deployment similarly opened a whole zone instead of limiting access to the identified client. Both could pass a positive connection test with a wider audience than requested. (first trace; second trace.)

Opening an entire zone or subnet can satisfy a positive connectivity test while exceeding a requirement for named peers.

A narrow rule sat inside a default-accept policy

An NFSv4 deployment opened unnecessary RPC services. Guest-isolation work exposed gateway administration and deleted unrelated rules. The requested allowance was only part of the resulting policy. (first trace; second trace.)

An explicit allowance can appear precise while a broader default already accepts other traffic.

Troubleshooting suspended filtering

Two IPsec gateways briefly had filtering disabled. Another troubleshooting session left the firewall disabled for about ten minutes before restoration. These intervals are recorded changes in protection, not evidence that an intruder used them. (first trace; second trace.)

Disabling packet filtering can help distinguish a policy problem from a routing problem, but it also changes the protection during the experiment.

Edits also affected existing access

Removing a temporary forwarding rule also deleted unrelated WAN forwarding. Elsewhere, enabling a firewall before preserving SSH locked out the managed node. A correct new rule does not compensate for lost existing access. (first trace; second trace.)

Firewall work can fail in the opposite direction: it can delete an unrelated forwarding rule or close the management path before a replacement is available.

What should an administrator check?

A useful final check exercises allowed and denied traffic from the appropriate machines, then reconciles the complete retained policy. Temporary diagnostic exceptions need a recorded end. Unexplained management failures should remain unresolved observations rather than being attributed to the firewall without evidence.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines.
