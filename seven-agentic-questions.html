The seven questions that tell you whether an AI agent actually worked

The transcript is not the work. The work is the change in the world—and the evidence that lets someone else trust it.

There is a moment in almost every agent demo when the room relaxes. The model has called a tool, produced a tidy summary, and announced that the task is complete. The cursor stops blinking. Someone says: “That’s pretty good.”

But an agent’s confidence is not an operational result. A polished answer can sit on top of a failed command, a half-applied change, or an assumption nobody checked. The useful question is not whether the agent sounded competent. It is whether the work can survive handoff to a skeptical person.

Ask questions that attach to reality

A practical evaluation starts by breaking the vague question—did it work?—into smaller questions with observable answers. Each one should point to an artifact, a log, a test, or an owner. If the answer is no, you should know what happens next.

“Done” is a claim about the world, not a mood in the transcript.

1. Did it understand the actual objective?

Not the first sentence in the prompt—the outcome that mattered. A task can be technically executed and still miss the reason it existed. Check the acceptance condition before judging the steps.

2. Did it operate inside its authority?

Agents need boundaries that are legible before they need more autonomy. Which systems could it touch? Which actions needed confirmation? An agent that “succeeds” by exceeding its mandate has failed a more important test.

3. Did it make the important state change?

Separate intent from effect. The command was issued; the service restarted; the record changed; the packet crossed the boundary. These are different facts. Verify the last one.

4. Can someone reproduce the path?

A useful run leaves an operational record: inputs, tool calls, outputs, decisions, and the final state. Reproducibility is not bureaucracy. It is how you turn a one-off success into a system property.

5. Did it notice and handle failure?

Every real environment returns ambiguity. Timeouts, partial writes, stale reads, permissions, and conflicting signals are not edge cases. The evaluation should reward an agent for stopping with a clear failure, not for improvising past one.

6. Is the evidence proportional to the stakes?

A low-risk formatting change and a production firewall rule do not need the same proof. Verification should scale with blast radius. “It looks fine” is not evidence for a consequential action.

7. Who owns the next decision?

The final question is about the boundary between automation and judgment. If the result is uncertain, the agent should route the uncertainty to a person with context, authority, and a clear next action. Escalation is not a failure mode; silent confidence is.

These questions are deliberately plain. Their job is to make a fuzzy success claim inspectable. The more capable the agent becomes, the more important that habit gets. Capability expands the set of things a system can change. Evidence tells us which of those changes actually happened.
