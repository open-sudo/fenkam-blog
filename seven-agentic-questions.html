Seven Questions for an AI Sysadmin Vendor

Ask for evidence of what the agent changes, what it preserves and how it recovers when work goes wrong.

In my experiment, an AI agent passed 837 of 905 sysadmin tasks. A separate review found unnecessary files or changes in 403 of the 905 runs. Those figures measure different things: completing the requested job and leaving the server in an acceptable state.

See the experiment and its records for the counts and examples.

1. Does it work on the software we actually use?

Ask for results by product, version and task. Good results on a current Linux release do not establish reliability on your older database or network appliance.

What counts as success? Ask to see checks of the final system against the original requirements, including restart tests where relevant. A command that exits successfully is not enough.

2. What stops it from making unsafe changes?

Ask how the product prevents secrets entering logs, unauthorized package sources, excessive permissions and security controls being left disabled. Which limits are enforced by tools, and which rely on instructions to the model?

Request examples of a blocked action. Does the agent stop, ask for help or try another way around the restriction? Who supplies and maintains those controls?

3. What happens when you repeat the task?

Ask how often the same instructions and starting conditions have been tested. Separate clean successes, successes with unwanted changes, failures and partly modified servers.

Look at the worst outcomes as well as the average. A claimed failure rate needs a sample size and an explanation of what was counted.

4. Can it resume interrupted work?

Ask for a long task interrupted halfway through. Can the agent identify what already succeeded, inspect the current state and continue without repeating destructive changes?

It must retain the original constraints as well as its progress. Ask what happens when its conversation history is shortened or an early decision proves wrong.

5. Can it coordinate changes across machines?

How many machines and simultaneous jobs have actually been tested? Ask how the product prevents conflicting changes to shared services.

Inspect a partial deployment: one node succeeds and another fails. Who coordinates recovery, and how does the agent establish which machines are safe to use?

6. Does it preserve what is already there?

Existing servers have schedules, exceptions and dependencies that may not appear in the new request. Ask how the agent records their starting state and checks that unrelated behavior still works afterward.

Request results from existing environments, not just clean installations. What does it do when it cannot explain a setting it wants to replace?

7. Can I inspect the evidence?

Ask for redacted task instructions, starting conditions, command logs and verification results. The examples should include failures and unwanted changes, with the model, tools and permissions identified.

If records cannot be shared, ask for a reproducible test in your own environment. A demonstration you can inspect is more useful than a success rate with no supporting examples.

Start with one task your team understands well. Review the commands and the machine afterward, including the changes that were not part of the request.
