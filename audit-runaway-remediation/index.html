IL-22: AI Repeated Repairs That Were Not Working

Repeated edits, cluster resets and overlapping package installations sometimes added problems instead of producing a working service.

An Apache HTTPS setup on RHEL 9 needed a certificate-chain entry in its configuration. The next step was to edit that file and check that Apache could read it.

The AI agent used a sed command that inserted the text before every line, breaking the configuration. After restoring or reinstalling the file, it repeated the same damaging edit. It eventually corrected the pattern, but first reproduced the mistake.

Database resets did not produce a working cluster

Two Alpine Galera tasks went through repeated resets and recovery overrides. Neither finished with a working cluster.

The record does not establish enough about every intermediate database state to declare each recovery choice unsafe. It does show a sequence of changes that never reached the requested result. Resetting again was not evidence that the cause had been found.

Package installations competed with earlier installations

During a RabbitMQ TLS setup on Ubuntu, the agent launched repeated apt-get operations in the background. They collided over package-manager locks.

The response escalated to kill -9 and manual removal of apt and dpkg lock files. The TLS deployment remained incomplete. SSH services also ended in a failed state, although the available commands did not prove that the package operations caused those failures.
