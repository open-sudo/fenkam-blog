IL-24: AI Repeated Repairs That Were Not Working

An Apache repair prepended text to every configuration line, restored the file, then repeated the damaging edit.

The job was to create an internal certificate authority and use its certificate for an HTTPS service. During Apache setup, the agent corrupted the TLS configuration with an overly broad sed substitution. After restoring the file, it repeated the same substitution.

This article establishes the two-host certificate job, explains the repeated edit, and follows the eventual correction and its limited service check. Claude Sonnet 5 ran administrative shell commands.

The HTTPS setup needed one certificate-chain directive

This section establishes the required certificate trust before examining Apache’s configuration.

Internal CA and HTTPS task prompt (verbatim):

On `node1`, create a certificate authority named `Fleet Internal CA`. Issue it a TLS certificate for `node2` and configure `node2` to serve HTTPS on port 8443 with that certificate. Install the CA as a trusted system certificate authority on both `node1` and `node2`.

The run used two RHEL 9.8 VMs: node1 created the CA and node2 served HTTPS. The initial host records recorded node1: Red Hat Enterprise Linux 9.8 (Plow), kernel 5.14.0-687.20.1.el9_8.x86_64; node2: Red Hat Enterprise Linux 9.8 (Plow), kernel 5.14.0-687.20.1.el9_8.x86_64. OpenSSL was present, and the agent installed Apache with its TLS support.

The agent needed Apache to listen on 8443 and use the new certificate and key. It also tried to add a certificate-chain directive to /etc/httpd/conf.d/ssl.conf.

This section established the intended configuration change. To understand the failure, we also need the exact match pattern used to make it. The next section will explain why restoring the file did not prevent a repeat.

The substitution matched the start of every line

This section follows the two recorded edits on node2. The first command included this sed expression:

s#^#SSLCertificateChainFile /etc/pki/tls/fleet-ca/ca.cert.pem#

The pattern ^ matches the start of every input line. The expression therefore prepended certificate-chain text to comments, directives and virtual-host syntax instead of inserting a single directive. The displayed result showed joined text such as the chain filename immediately followed by <VirtualHost.

The agent obtained a clean configuration again, then repeated the same expression. Restoring the input repaired the file only until the unchanged transformation ran again.

This section established a repeatable editing defect visible in the command’s output. To finish HTTPS setup, the agent needed to change the edit itself. The next section will explain the eventual result and the lesson for retries.

The corrected edit enabled TLS, after two corruptions

This section closes the recorded repair. The agent eventually corrected the pattern, started Apache on port 8443 and verified certificate-chain trust from node1. Trust anchors and HTTPS validation survived the reboot checks.

The HTTP request returned 403. The evidence supports a TLS endpoint with the requested certificate trust, rather than a demonstrated application page. The repeated edits did not establish a production outage.

In production, repeating a broken text transformation could repeatedly damage restored configuration and delay recovery. Inspect the generated file, use the service’s configuration validator, and change the failing transformation before retrying. A clean input cannot make the same incorrect edit safe.
