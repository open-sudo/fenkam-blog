IL-22: AI Troubleshooting Repeated Changes Without Resolving the Fault

Repeated edits, cluster resets and overlapping package installations sometimes added problems instead of producing a working service.

While configuring HTTPS, an AI agent used sed to edit Apache’s configuration. The command inserted certificate-chain text before every line and broke the file. After reinstalling or restoring the configuration, the agent repeated the same damaging edit. It eventually corrected the pattern, but first reproduced a mistake it could have inspected.

Imagine a tailor repeatedly cutting a garment shorter because the first alteration did not fix the fit. Each attempt changes the starting point and leaves less material for repair. Repeated edits and resets can do the same to a host, especially when new attempts begin before the effects of earlier ones are understood.

The same edit broke Apache twice

The RHEL 9 record showed two substitutions that prepended text to every line of ssl.conf. Repeating the installation did not change what the faulty substitution would do.

The useful next step after the first failure was to inspect the generated file and test the edit on a copy. Repeating the sequence added work without testing a new explanation.

Database resets did not produce a working cluster

Two Alpine Galera tasks went through repeated resets and recovery overrides. Neither finished with a working cluster.

The record does not establish enough about every intermediate database state to declare each recovery choice unsafe. It does show a sequence of changes that never reached the requested result. Resetting again was not evidence that the cause had been found.

Package installations competed with earlier installations

During a RabbitMQ TLS setup on Ubuntu, the agent launched repeated apt-get operations in the background. They collided over package-manager locks.

The response escalated to kill -9 and manual removal of apt and dpkg lock files. The TLS deployment remained incomplete. SSH services also ended in a failed state, although the available commands did not prove that the package operations caused those failures.

Before another corrective command, establish what is running, what the last command changed and what the next command is meant to test. If those facts are unclear, capture the current state first. Several plausible repairs in flight can make the original fault harder to identify.

These examples come from recorded lab tests in which an AI agent could run commands on Linux machines. Case evidence. The source records contain the commands and the observations used here.
