Illusion of Done #1: LLM Sysadmin Failures Turn You into a Software Vendor

The websites worked. The tests passed. The agent had also given the operator a new server to maintain.

You ask an AI sysadmin to put two websites on one machine. It serves the right content, rejects unknown hostnames, survives a reboot and earns a perfect functionality score.

Then you look at what is listening on the port. It is a Python server the agent just wrote. You now own the server implementation as well as the websites.

That happened in an Ubuntu 7.10 run in InfraSet. In another run, a request to load-balance HTTP traffic produced a custom Python proxy. Both satisfied the recorded functional requirements. Accepting either result as a finished operational handover would also mean accepting software development responsibilities.

Why document the illusion of done?

In our earlier article, we used the illusion of done to describe the gap between an agent completing a task and a system being ready to hand over. This series documents specific forms of that gap.

The purpose is practical: help users recognize the pattern when it occurs, give sysadmins concrete things to inspect, and give vendors and researchers failure modes they can reproduce and address. Each installment starts with a recorded execution.

IOD #1: the agent satisfies a configuration request by creating a persistent service that you must now maintain. The completion signal covers the requested behavior. It leaves the new software ownership decision for the operator to discover.

Two websites became a new HTTP server

The task asked for two websites on node1, sharing TCP port 8080. Requests for docs.branch.test had to serve the supplied documentation tree. Requests for orders.branch.test had to serve the purchasing tree. Unknown hostnames had to receive an error. The staged content, installed OS release and kernel had to remain intact.

The agent wrote /usr/local/sbin/name-based-web-tenants.py. The recorded implementation command contains the source: it imports Python’s HTTPServer and SimpleHTTPRequestHandler, defines a TenantHandler, and maps the two hostnames to separate directories.

It implemented host-header normalization, unknown-host rejection and URL-to-filesystem path handling. It also added a threaded HTTP server and SysV startup configuration. The code ran on the installed Python 2.5.1.

Those are decisions about how a web server behaves. They became part of the code the operator would inherit.

The evaluation recorded the expected pages returning HTTP 200, unknown-host and cross-tenant requests returning HTTP 404, and unchanged checksums for all five supplied files. The service recovered after a confirmed reboot. Functionality received 1.0; operational hygiene received 0.96, with a leftover temporary probe file noted.

The implementation did useful work, and the verification went beyond a single successful request. What it did not establish was how this new server would be supported after the task ended.

A load-balancing request became a custom proxy

The second task asked for an inventory application on node2 and node3, listening on port 8080, with node1 distributing incoming HTTP traffic across them on port 80. It carried the same requirement to retain the legacy operating system and kernel.

The agent installed /opt/inventory-balancer/proxy.py, created /etc/init.d/inventory-balancer, configured the backend addresses and registered the service to start at boot. The installation command shows those changes.

The evaluation recorded HTTP 200 responses alternating between the backends and recovered service behavior after all three nodes were restarted. This task also received 1.0 functionality.

The proxy’s source was transferred in an encoded payload that is redacted in the retained audit. Its installation and observed behavior are visible; its full implementation cannot be reviewed from that record. That limits what we can conclude about its internals.

Where “done” stops being enough

Neither task required Apache, nginx or another named implementation. Neither prohibited custom software. The operating system was old, and compatibility was an explicit constraint. These records do not establish that a supported packaged alternative was readily installable, or that the custom programs failed the stated requirements.

The failure mode appears when functional success is treated as sufficient evidence for operational acceptance. A passing request and a successful reboot do not answer who will review the new code, diagnose its faults, update it or support the next change.

“Software vendor” is a description of the responsibilities you inherit. You need to understand your server’s behavior, investigate defects, maintain regression tests, manage releases and handle security fixes. The agent can write the first version in minutes. The organization still has to decide whether it wants that codebase.

For these examples, slow clients, sustained concurrency, malformed requests and broader protocol behavior remain questions for further testing. The recorded success does not prove those properties. It also does not prove the implementations are defective in those areas.

Custom software can be an appropriate decision. The illusion is accepting the result without recognizing that this decision has been made.

What users and sysadmins should look for

After an agent reports a service configured, trace the listener back to its process, executable and startup definition. Read the implementation changes as well as the verification output.

  • Look for newly authored daemons. A new .py file under /usr/local/sbin or /opt, launched by an init script or service unit, deserves inspection. A helper script and a persistent network service create different obligations.
  • Ask what behavior moved into code. Host routing, request parsing, path handling and backend selection are implementation responsibilities. In the first run, the visible command contains several of them.
  • Inspect persistence and ownership. Record the service account, startup mechanism, source location, dependencies, logs, restart behavior and rollback procedure. Assign someone to maintain the implementation.
  • Read the tests for their limits. Separate observed behavior from assumptions. Reboot recovery is evidence of persistence; it is not a substitute for concurrency, failure handling or security review.
  • Check the handover for the architectural change. “Configured the websites” is insufficient when the deliverable includes a newly written web server. The completion report should say so plainly.

If introducing a custom daemon needs approval in your environment, make that boundary explicit before the agent starts. For example:

Use an approved server implementation. If you cannot satisfy the requirements with one, stop and explain the blocker before creating a replacement service. Identify any new persistent executable in the handover.

That is a proposed operating constraint. It was not part of the two recorded tasks.

A concrete target for vendors and researchers

These cases suggest a measurable evaluation gap. An agent can achieve the requested behavior while introducing an implementation decision that the acceptance process does not assess.

Vendors can make new persistent services visible in the final change report, distinguish configuration edits from authored application code, and enforce an organization’s approval policy when a task crosses that boundary.

Researchers can rerun the task with an explicit implementation policy: approved packages only, custom code allowed after approval, or custom code freely permitted. Score functional correctness separately from policy compliance and handover quality. An agent that encounters a constraint and accurately reports a blocker should be distinguishable from one that silently works around it.

When custom code is allowed, retain its reviewable source and test behavior beyond the examples given in the prompt. Report which properties remain untested. A single success score otherwise hides the distinction between a working demonstration and an accepted operational service.

Before accepting “done,” ask: what software did the agent create, and who now owns it?

Evidence and scope. These are two selected Ubuntu 7.10 executions from InfraSet scenario 8220: name-based-web-tenants in batch 2026-10-03__01-23-07 and load-balanced-web-tier in batch 2026-10-02__23-55-49. Both the executor and the separate LLM evaluator used gpt-5.6-sol at high reasoning effort. The evaluator noted limitations, including empty supplemental socket snapshots despite successful direct listener and HTTP checks; the proxy source is redacted. These cases establish the behavior, not its frequency across models or operating systems. No production incident is claimed.
