LLM as sysadmin builds its own crazy software to meet requirements

When your AI decides to become a software vendor.

Ask an AI agent to get a service working, and it may write the service itself.

That happened in two Ubuntu 7.10 runs I examined. A request to load-balance HTTP traffic produced a custom Python reverse proxy. A request to restore local mail delivery produced a custom SMTP daemon. The agent installed both as persistent services and demonstrated their recovery after restarts.

Both tasks received full functionality scores. Both also left behind software that somebody would now have to maintain.

A load-balancing request produced a new proxy

The request described an ordinary three-machine deployment:

Run the inventory web application on node2 and node3, each listening on port 8080. Configure node1 to load-balance incoming HTTP requests across both backends on port 80.

The task also required retaining the installed operating-system release and kernel. It did not prescribe a particular load balancer.

The agent created Python 2.5 applications for the two backends and wrote a reverse proxy to /opt/inventory-balancer/proxy.py. It installed an /etc/init.d/inventory-balancer startup script. Its execution report describes round-robin distribution and retrying the other backend when one fails.

The recorded evaluation confirms requests reaching both backends, recovery after a backend interruption, and service recovery after sequential restarts of all three machines. Changed boot identities corroborated those restarts.

This was a running service with startup configuration and observed recovery behavior. Accepting the result would also mean accepting responsibility for that proxy’s implementation.

The proxy source was transferred as an encoded payload that is redacted in the audit. Its destination, installation and behavioral evidence remain visible. Those records establish the custom implementation, but do not allow a complete source review.

A mail-delivery request produced a new SMTP daemon

The second task asked:

Restore local mail delivery for branch.test on node1. Mail sent from node2 to helpdesk@branch.test should reach both the alice and bob local mailboxes; accounts@branch.test should reach bob only. Unknown recipients should be rejected, and relaying for unrelated domains should be rejected. Preserve the sample messages and routing handover in /srv/legacy2/smtp-alias-delivery.

Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The agent inspected the installed Python SMTP support, then wrote /usr/local/sbin/branch-smtpd.py. The visible source imports smtpd, asyncore, fcntl and pwd, and defines BranchSMTPChannel and BranchSMTPServer.

The implementation needed debugging. Early delivery attempts failed. A later command replaced an os.fchown(...) call with os.chown(...), restarted the daemon, and checked its port-25 listener. The evaluator records that the compatibility defect was corrected and empty mailbox state from the failed attempts was cleaned before final testing.

The final evidence showed the required delivery, alias routing and rejection behavior. The handover files were preserved, and the service recovered after node restarts. The evaluator awarded full marks.

The agent had moved from administering a mail service to developing, debugging and deploying one.

The implementation becomes part of the handover

There is real capability here. The agent used an old runtime to build useful services, corrected a compatibility problem and made the results persistent. The requests left implementation choices open, so custom software was a legitimate way to satisfy them.

That freedom also changes what the operator receives. Alongside the requested behavior comes a codebase with an owner to assign, faults to diagnose and future changes to manage.

A working proxy still raises questions about slow clients, concurrent requests and malformed HTTP. A working SMTP daemon raises questions about full disks, interrupted deliveries and protocol edge cases. The recorded tests do not establish all those properties. They also do not establish that the programs fail them.

The operational concern is the responsibility introduced by the implementation. A short request can result in a service whose behavior the organization must now understand well enough to support.

If approved software is a requirement, it belongs in the task or operating policy. If custom services are acceptable, their introduction should be explicit in the handover, together with their source, tests, limitations and maintenance ownership.

The useful question after an agent reports success is: what software did it create to get there?

About these examples. These are two recorded Ubuntu 7.10 tasks from InfraSet, executed by gpt-5.6-sol at high reasoning effort. The evaluator used the same model and effort. The evidence extract contains the requests, selected commands, source paths and evaluator findings for these two cases. They demonstrate the behavior; they do not establish how frequently agents choose custom implementations or whether these services are production-ready. The experiment lives in InfraSet.
