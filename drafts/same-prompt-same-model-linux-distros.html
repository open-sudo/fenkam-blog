Same Prompt. Same AI. Widely Different Implementations Across Linux Distros.

On some systems, the AI configured a packaged web server. On RHEL9, it repeatedly wrote its own—even with Apache and nginx available.

The same request can turn an AI into two different kinds of operator. On one machine, it installs and configures a web server. On another, it writes one.

We observed that difference while running the same HTTPS task through gpt-5.6-sol, at high reasoning effort, across Linux environments in InfraSet. Ubuntu, Alpine, and CentOS Stream produced conventional package-based deployments. A RHEL10 rerun did too. On RHEL9, the agent repeatedly chose a custom Python service.

The strongest example came after we addressed subscription initialization. Apache and nginx were available on the RHEL9 machine. The agent never checked.

The exact request

This is the complete task prompt, verbatim:

On `node1`, serve HTTPS on port 8443 with a certificate that is renewed
automatically before it expires, and have the service pick up each new
certificate while it keeps answering requests.

Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The executor also received shared infrastructure instructions, including a requirement to reboot the node and demonstrate recovery. The public task text was identical across the six environments compared below. The model and reasoning-effort settings were the same; installed tools, operating systems, and repository conditions differed.

Where it configured an existing server

The recorded Ubuntu 7.10 run eventually used Apache, after trying other packaged components. Ubuntu 24.04, Alpine 3.23, and CentOS Stream 10 used nginx. Each produced a conventional web-server deployment, with custom renewal scripts around packaged TLS and HTTP software.

RHEL10 also behaved as expected once repository access was available. In the rerun, subscription initialization completed with a 30-second pause. The agent checked the repositories, found BaseOS and AppStream, and ran:

dnf -y install --setopt=install_weak_deps=False httpd mod_ssl openssl

It configured Apache on port 8443, generated a 30-day self-signed certificate, and scheduled renewal checks twice daily with a seven-day threshold. Apache picked up replacements through a graceful reload. The recorded rotation test completed 150 requests without failure, and the deployment recovered after reboot. The evaluator awarded full functionality marks.

That matters because the earlier RHEL10 attempt had encountered unavailable repositories and built custom software instead. Restoring access was followed by a conventional implementation. This supports package availability as a contributor in that case; the rerun does not isolate whether the pause itself was necessary.

RHEL9 chose another route

In the earlier RHEL9 run, the agent announced: “I’ll use only these installed components: a small TLS server that reloads certificate material in-process, plus a systemd renewal timer.” The task never imposed that restriction.

We repeated the task with subscription initialization enabled and the same 30-second pause. After one inventory command, the agent began creating its own certificate-renewal script and Python HTTPS service. It did not query repositories or attempt a package installation.

We independently checked the same live VM while the run was underway. Both BaseOS and AppStream were enabled. A successful dnf list --available httpd mod_ssl nginx returned Apache 2.4.62, mod_ssl 2.4.62, and nginx 1.20.1. This check establishes availability at inspection time; it was separate from the agent’s execution and did not install a server.

The agent used Python’s existing HTTP and TLS libraries and the OpenSSL command for certificates. It wrote the service and its integration, rather than implementing TLS cryptography from scratch. Its server loaded certificate material for new connections, with seven-day certificates and renewal checks every six hours.

The result worked in the recorded tests. After correcting certificate-directory permissions, it served HTTPS, completed 100 requests without failure during rotation, and recovered after reboot. It received full functionality marks too.

“But the prompt is vague”

That is a fair objection. The request specifies behavior, not a product. It does not require Apache or nginx, forbid custom software, or state a maintenance policy. The custom implementation is not, by itself, a violation.

Yet the same wording led to packaged web-server deployments across the observed Ubuntu, Alpine, CentOS Stream, and corrected RHEL10 runs. It was sufficiently specific to produce the conventional implementation in those environments. RHEL9 repeatedly took a different path, including a run where an independent check confirmed packaged alternatives were available.

The finding is inconsistent implementation choice under the same stated requirements. “Serve HTTPS and rotate certificates” can mean configuring maintained software, or delivering a new service whose source code someone must own. Both can pass the same functional checks. They are different operational handovers.

The phrase “legacy platform” may have encouraged a preference for installed tools, even on modern RHEL9. Expectations about subscriptions may also have influenced the choice. Neither explanation is established by these traces. The RHEL9 agent did not record a comparison of the packaged and custom alternatives.

What the comparison establishes

This is an observed pattern across selected runs, not a claim that a distribution determines the answer. Models are nondeterministic. Repository access and installed packages also vary. Repeated controlled runs would be needed to measure how often each approach occurs and which environmental differences cause it.

For operators, the practical lesson is that functional success does not tell you which implementation you will inherit. If using approved packaged services matters, say so in the operating policy. If custom services are allowed, their introduction deserves an explicit decision and a clear maintenance handover.

The agent demonstrated that it could make HTTPS work. The unresolved question is why, with a packaged server available, it decided that making HTTPS work required becoming the server’s author.
