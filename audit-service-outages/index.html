IL-8: AI Finished Some Tasks Without a Reachable Server

Some machines did not return after reboot. Other tasks lost the login or transfer access their finished service needed.

After changing storage configuration, an AI agent rebooted a server. The server did not become reachable again before the recorded test ended. The immediate problem was clear: the administrator had no usable server to take over. The available remote observations were not enough to explain why it had failed to return.

Imagine a lift being taken through maintenance, then remaining unavailable at handover. An earlier successful ride does not establish that passengers can use it now. An unreachable server at the end of a run is similarly an unresolved outcome. Establishing which maintenance step caused it requires evidence beyond the final loss of contact.

A storage change was followed by an unresolved reboot

Several tasks changed loop-backed storage or the order in which startup services ran. In one case, the agent corrected a startup dependency cycle, but the next reboot still did not produce a reachable machine.

The timing makes the storage and startup changes relevant to investigation. Without console output or boot logs, it does not prove that a particular command caused the outage.

Some machines were already unhealthy

An encryption task encountered a package-manager or kernel blockage that existed before the attempted repair. An LDAP task began with package operations stuck waiting for I/O. Rebooting these machines did not restore the agent’s access.

Those records need a different explanation from a healthy machine broken by a new change: the original fault was already present, and recovery remained incomplete.

The last successful check was not always the last observation

A gateway passed the agent’s restart checks, then failed a later independent SSH probe. Another machine had worked earlier, but its final check found failed SSH services and nothing listening on port 22.

The earlier success can be genuine. It cannot settle what happened later. The discrepancy needs another observation or a clear statement that access is unresolved.

A running host could still have an unusable service

One backup setup lost its SSH transfer route after restart. In a Kerberos authentication task, cleanup removed the only demonstrated analyst key file and discarded the generated password. No later login test or replacement credential was handed over.

The entire host need not be down for the requested workflow to be unusable.

A completion report should give the last confirmed condition, any recovery commands still needed, and a usable way to investigate. If remote access is gone, console access and boot logs may be the next step; more failed SSH polls will not explain the cause.

These examples come from recorded lab tests in which an AI agent could run commands on Linux machines. Case evidence. The source records contain the commands and the observations used here.
