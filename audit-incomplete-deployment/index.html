IL-25: AI Left Deployments Unfinished

Certificate files, partial database settings and successful pings were reported around services that had not actually been completed.

I wanted a PostgreSQL primary with two standbys, so the database would have a recovery path after a primary failure. That required preparing the standbys as well as configuring the primary.

An AI agent changed some primary settings but did not finish replication access or initialize the standbys. Both standby services remained stopped. The setup was missing the machines it depended on for failover.

The primary settings did not create the standbys

Creating a PostgreSQL standby requires more than changing settings on the primary. The standby needs the initial database contents, a replication identity and permission to connect.

Those steps were unfinished in the Ubuntu 24 task. The final observations showed only a primary listening on loopback and two stopped standbys. The record describes an incomplete new setup; it does not establish destruction of a previously healthy production cluster.

Certificates existed, but RabbitMQ still served plain AMQP

Another Ubuntu task generated certificates for a RabbitMQ TLS deployment. It did not distribute them to the required servers or configure the broker’s TLS listener.

The final listener was the ordinary unencrypted AMQP port. Generating certificate files was useful preparation, but clients still had no completed encrypted broker endpoint to use.

Recorded commands

Pings succeeded over networking that already existed

A RHEL 9 network task left the requested LAN unconfigured. The successful pings went to a DHCP management address on a segment the machines already shared.

Those replies proved the existing management connection worked. They did not show that the agent had built the additional routed LAN.

Complete the missing standby, TLS listener or LAN before testing the parts that depend on it.
