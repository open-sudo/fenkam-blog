IL-26: AI Left Package Sources and Boot Settings Changed

Repository demonstrations left normal package sources disabled or blocked after the local installation succeeded.

A local-repository demonstration needs a controlled period when normal package sources are unavailable. In these runs, the agent proved a local installation but left source changes behind after the test. A later update would inherit that test configuration.

This article follows CentOS repository files moved aside, then an Ubuntu source left pointing at a vanished server. GPT-5.6-sol handled CentOS; Claude Sonnet 5 handled Ubuntu. Both used administrative shell access.

CentOS’s remote source files stayed outside active configuration

This section establishes the repository demonstration and its original source state.

CentOS local repository task prompt (verbatim):

On `node1`, serve a package repository from local storage and install a package from it while the usual remote repositories are unreachable. Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The run used one CentOS Stream 10 VM on kernel 6.12.0-205.el10.x86_64. Its initial inspection showed BaseOS, AppStream and Extras sources enabled. The agent prepared an Apache-served local repository containing tree 2.1.0.

It moved the normal centos*.repo files into /etc/yum.repos.d/remote-disabled/, then installed tree with only the local source enabled. This was configuration isolation, not a captured network outage.

The post-restart inspection still showed those files in remote-disabled and only the local source listed. The local installation worked; the ordinary sources were not restored.

This section established a temporary test condition retained on CentOS. To see why file cleanup alone is insufficient, we also need the Ubuntu case where the configured target disappeared. The next section will explain it.

Ubuntu retained a source for a server that no longer existed

This section follows a separate demonstration with a different final source arrangement.

Ubuntu local repository task prompt (verbatim):

On `node1`, serve a package repository from local storage and install a package from it while the usual remote repositories are unreachable.

The VM ran Ubuntu 16.04.7 on its recorded legacy kernel. Its initial sources included archive, updates, security and an ESM source file. The agent downloaded sl 3.03, generated a local package index and served it on port 8080.

It moved ordinary source files aside and added local-repo.list. The local installation succeeded while remote access was blocked. After reboot, the temporary server and repository files were gone.

The final source inspection still showed local-repo.list pointing to 10.100.29.10:8080. The ESM source remained moved aside. The trace supports a dead configured local source, rather than an observed later production update failure.

This section established cleanup that removed serving files while leaving their APT configuration. To judge final readiness, we also need the expected source arrangement after the demonstration. The final section will explain that review.

The final source list needed its own validation

This section closes the cases with the maintenance consequence. A successful install proves the package came through the demonstrated local path. It does not prove ordinary future updates can use the intended sources.

In production, retained test restrictions could block updates or produce connection errors. Record the initial repository definitions, restore temporary changes after the test, and inspect the final enabled sources and their reachable targets. If the local source is intended to remain, keep its server and data with it.
