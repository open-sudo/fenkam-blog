IL-29: AI Discarded a Worker’s Error Output

The worker ran, but its systemd unit discarded standard output and standard error.

I wanted a background worker on RHEL 10 to run under the unprivileged inventorysvc account inside a chroot. Restricting the worker’s access still left an operational need: its errors had to reach somewhere an administrator could read them.

The AI agent delivered a systemd unit that discarded both standard output and standard error. Messages written to those streams would therefore be lost even if the process itself stayed healthy.

The files inside the chroot did not establish a logging path

The chroot contained logging-related socket placeholders. That suggested where messages might be sent, but did not demonstrate a connection to a working collector.

The missing check was to make the actual confined worker emit a recognizable message, then retrieve that message from the intended log destination. Seeing a socket path or a running process did not perform that check.

The conclusion concerns the discarded streams

The record did not establish that every application-specific log file or host-level observation was absent. It showed that the delivered service unit discarded the worker’s usual output and error streams.

Documentation

The service needed a demonstrated route from an error in the worker to a retained message, including after restart. Without that route, the next administrator could inherit a running service with its ordinary diagnostic output missing.

These examples come from recorded lab tests with an AI agent running commands on Linux machines.
