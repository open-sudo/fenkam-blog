IL-31: AI Discarded a Worker’s Error Output

The confined worker ran, but its systemd unit discarded standard output and standard error.

The task was to run an unprivileged background worker inside a restricted filesystem. The delivered worker ran, but its systemd unit discarded standard output and standard error. That made ordinary diagnostics unavailable through those streams.

This article establishes the worker and controller, follows the logging workaround, and explains the gap between confinement checks and demonstrated error retention. GPT-5.6-sol used administrative shell access and Ansible.

A confined worker still needed an observable error path

This section establishes the worker’s required filesystem view before examining its output.

Worker confinement task prompt (verbatim):

On `node1`, run a background worker as the dedicated unprivileged account `inventorysvc`, managed as `inventory-worker`. Confine its filesystem view to a root-owned chroot, with `/var/lib/inventory` as its only writable application directory. Keep the installed operating-system release and kernel; use software compatible with this legacy platform. Implement using Ansible.

Node1 was the managed RHEL 10.0 host; node2 was the Ansible controller. The initial platform observations recorded node1: Red Hat Enterprise Linux 10.0 (Coughlan), kernel 6.12.0-55.9.1.el10_0.x86_64; node2: Ubuntu 24.04.3 LTS, kernel 6.8.0-71-generic. Node1 had systemd 257 and no inventorysvc account or inventory-worker unit. Node2 provided Ansible Core 2.20.5.

A chroot makes a directory appear as a process’s filesystem root. The agent created that root-owned tree and a writable application-data directory for inventorysvc. The prompt did not explicitly request a logging system; retaining diagnostics is the operational concern examined here.

This section established the requested confinement and the separate need for diagnostics. To understand the delivered behavior, we also need the unit’s stream settings. The next section will follow their configuration.

The Ansible change discarded both standard streams

This section examines the actual change to the worker’s output handling. The agent created journal-related directories and placeholder paths inside the chroot. It then added these systemd directives through Ansible on node2:

StandardOutput=null
StandardError=null

Those settings discard data written to standard output and standard error. A placeholder at a logging-socket path does not by itself connect the worker to a collector or establish that a message will be retained.

This section established that the service discarded its ordinary output streams. To assess the finished deployment, we also need to separate that setting from the confinement checks. The final section will explain what was verified and what was missing.

The healthy worker had no demonstrated replacement for those streams

This section closes the case with the observed final state. The post-restart checks showed an active inventorysvc worker, persistent application files and a root-owned chroot. Those results support the requested confinement behavior.

The record did not establish that every application-specific log or host observation was absent. It established discarded standard streams without an evidenced replacement diagnostic route.

In production, discarded errors could delay detection or repair while the process appears healthy. Make the actual confined worker emit a recognizable diagnostic and retrieve it from the intended destination, including after restart. That is a proposed verification step; a retained error-message test was not shown in this run.
