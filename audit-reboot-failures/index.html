IL-14: AI Setups Needed Repairs After Reboot

A SONiC bridge joined two Ubuntu clients, disappeared on reboot and needed manual reconstruction.

The task was to join two network segments so hosts could communicate directly through a layer-2 bridge. Claude Sonnet 5 created a working bridge with live commands. Restarting the forwarding machine removed it, and manual reconstruction restored connectivity.

This article establishes the mixed switch-and-client topology, follows the reboot failure, and explains why the final successful ping proved manual recovery. The agent used administrative shell access.

A SONiC host joined two Ubuntu clients

This section establishes the actual machines rather than inferring their operating systems from the task’s Ubuntu label.

Transparent layer-2 bridge task prompt (verbatim):

`node2` and `node3` are attached to two different segments of `node1`. Join those segments into a single layer-2 domain, so the two hosts share one subnet and reach each other directly with `node1` forwarding frames rather than standing in the path as a routed hop.

Node1 ran SONiC on Debian 13 with kernel 6.12.41+deb13-sonic-amd64. Node2 and node3 ran Ubuntu 24.04.3 with kernel 6.8.0-71-generic. Node1’s eth1 and eth2 led to the two client segments; a separate management network carried command access.

The initial interface listing contained no br0. The agent created it using ip link, attached eth1 and eth2, and brought all three interfaces up. The clients used 192.168.50.0/24. Learned MAC addresses and TTL-preserving pings supported actual layer-2 forwarding. Bridge creation · Bridge address and forwarding database

This section established a working live bridge. To assess operational persistence, we also need the state after restart. The next section will follow that check.

Restart removed the live bridge

This section examines the lab’s additional restart check. The quoted task did not explicitly require reboot persistence; the test nevertheless exposed what an operator would need after restarting the switch.

After node1 rebooted, its listing showed no br0 and eth1 and eth2 were down. There was no saved bridge setup to recreate the imperative commands automatically. Node1 immediately after reboot

The agent then recreated br0 and its member links manually. A four-packet ping succeeded, and the forwarding database again learned the client MAC addresses on different ports. Manual reconstruction · Four successful replies after repair

This section established loss at boot and successful manual reconstruction. To deliver automatic recovery, we also need a persistent setup and a new restart test. The final section will explain what remained unproved.

The final ping followed intervention

This section closes the case by separating two outcomes. The bridge provided the requested forwarding when configured. The reboot demonstrated that the delivered setup did not recreate itself, and the final checks followed rescue commands.

On an operational network, that gap could leave the segments disconnected until someone reapplied the setup. Save the bridge through the platform’s supported persistent configuration and inspect forwarding after another restart, before any repair commands. That additional successful test was not recorded here.
