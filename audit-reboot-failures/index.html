Recovery Worked Only After Another Manual Command

Live routes, service startup, temporary storage and router credentials failed to return automatically.

The route returned after reboot, but only after the agent ran another command. The service came back, but only after a manual start. Those are useful recoveries. They are different from showing that the delivered setup restores itself automatically.

Live network state was not durable configuration

A bridge created with live ip commands disappeared after reboot. An ECMP route also required manual reapplication after restart. Both worked before the restart without having a proven durable representation. (first trace; second trace.)

A bridge or route created by imperative commands can work until restart.

The startup mechanism ran without producing the required route

A route was absent despite an active setup service, and pings showed complete loss until manual repair. Another router recovered only one multipath route; its later startup fix was not reboot-tested on that router. (first trace; second trace.)

An active oneshot unit is a statement about a command having run, not proof that the final path exists.

The service depended on a process or path that disappeared

An HTTP server launched with nohup was absent after reboot and had to be started again. Nginx in another task was enabled but returned inactive after restart. Network recovery alone did not restore the application. (first trace; second trace.)

A nohup process, an ephemeral document root and an enabled-but-inactive service fail in different ways.

Automation access and firewall identity also needed persistence

A firewall-zone regression was repaired after reboot, but the affected node was not restarted again. A VyOS setup lost controller credentials because keys had been written into a runtime home directory rather than persisted through its configuration. (first trace; second trace.)

Router login credentials and interface-zone bindings are part of recovery when the continuing deployment depends on them.

What should an administrator check?

Record what returned automatically, what required intervention and whether the final repair was restart-tested. A successful reboot of a different node cannot validate the repaired node’s startup path. Manual rescue is valuable evidence of recoverability, but it should remain distinct from automatic restoration.

Evidence. These examples come from recorded tests in which an AI agent received a Linux administration task and command access to isolated machines. The source extract includes all 12 cases grouped under this topic, their commands and assessment references, and the limits of each finding. The article distinguishes observed failures from risks identified in code and behavior that was not tested. No production attack is claimed. Original records are available in InfraSet.
