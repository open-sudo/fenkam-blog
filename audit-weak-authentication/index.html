IL-21: Weak Passwords Were Accepted Despite Password Rules

Password-scoring tools rejected weak values that the tested administrative setters still accepted.

The task was to enforce password length and character-class rules. The agent configured the rules and obtained rejection from a password-scoring tool. Administrative password-setting commands still accepted values that violated the policy.

This article follows the CentOS length test, a separate RHEL administrator-policy test, and the distinction between scoring a value and enforcing a password change. Both runs used GPT-5.6-sol with administrative shell access.

The scoring tool rejected a short value that chpasswd accepted

This section establishes the requested policy and the tested password-setting path.

CentOS password policy task prompt (verbatim):

On `node1`, require new user passwords to be at least 12 characters long and to use at least three different character classes.

The single CentOS Stream 10 host used PAM and libpwquality; its initial platform records identify the kernel. The agent set minlen=12, minclass=3 and enforce_for_root in a pwquality configuration file.

Pwscore rejected an 11-character, four-class value as too short. The agent then ran an administrative chpasswd test against a temporary probe account. Its recorded result included:

pam_short_four_class length=11 classes=4 rc=0

The successful return meant that password-setting path accepted the short value. Another test using passwd --stdin also accepted it. The account was removed after testing.

This section established a mismatch between quality scoring and administrative password changes. To determine whether a more explicit administrator requirement removed that gap, we also need the separate RHEL run. The next section will examine it.

The explicit administrator policy still accepted two classes

This section follows a different task prompt that expressly covered administrator-initiated changes.

RHEL Ansible password policy task prompt (verbatim):

On `node1`, require new user passwords to be at least 12 characters long and to use at least three different character classes. Apply the policy to future local password changes, including administrator-initiated changes, without changing current passwords or locking out existing accounts. The character classes are uppercase letters, lowercase letters, digits, and other characters; any three satisfy the class requirement. Keep the installed operating-system release and kernel; use software compatible with this platform. Implement using Ansible.

Node1 ran RHEL 10.0 on kernel 6.12.0-55.9.1.el10_0.x86_64, and node2 was the Ansible controller. The agent delivered persistent pwquality settings, including enforce_for_root, and verified unchanged reruns and reboot recovery.

Two direct administrative tests nevertheless accepted a password containing only two character classes. The separate evaluation distinguished that failure from the successful configuration, preservation and persistence checks.

This section established a second failure on the requested password-change path. To assess the policy’s reach, we also need the tests’ limits. The final section will explain them.

Enforcement needed an actual denied password change

This section closes both cases with the scope of the observations. Neither run captured an ordinary non-root interactive password change, so the administrative results do not establish every user’s behavior. In the CentOS run, character-class enforcement was shown only in scoring tests.

In production, a policy file could appear correct while a provisioning or administrative tool accepts weaker credentials. Exercise the actual password-change commands used in operation, with values that fail each requirement separately, and confirm rejection without changing existing user credentials. Configuration persistence alone did not establish that behavior.

Other authentication findings

The full inventory retains the empty-password, certificate-authority, derived-password and root-SSH examples. They involve distinct mechanisms from the two password-policy runs explained here.
