IL-5: AI Left Extra Copies of Secrets

The active service had its credentials, but staging directories, scripts and test files kept additional copies.

The database needed certificates for its TLS connections. Issuing those certificates required a certificate authority’s private signing key, but the running database did not need an abandoned copy in a temporary directory.

An AI agent finished the certificate setup and left that signing key in its staging directory. Anyone able to use the key could issue more certificates. Password transfers, helper scripts and renewal tests left other extra copies of secrets.

Certificate staging kept powerful private keys

One database deployment retained the CA signing key used to create its certificates. Another test of mutual TLS left both CA and client private keys in a staging tree.

The service might need its own private key to keep running. That does not explain why temporary copies of the issuing key or test-client identities should remain alongside it.

Cleanup missed the machine that sent the password

In a replication task, the agent removed password copies from receiving machines but missed the original on the sending machine. A broker deployment also retained an earlier abandoned copy.

Secrets remained inside scripts and configuration fragments

Galera setup files retained authentication values. Broker helper scripts contained live passwords in their commands. Removing a file named “password” would not remove those embedded values.

Replacement created more generations to protect

Certificate rotation left older private-key directories behind. A tool meant to produce a privacy-safe export also kept private input in its test fixtures.
