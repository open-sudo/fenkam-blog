Illusion of Done #1: Your AI Sysadmin Builds Crazy Software Instead of Configuring Apache or Nginx

A request for two websites became a custom Python HTTP server. It passed the tests, but left the operator with a codebase to maintain.

When I ask an AI sysadmin to put two websites on a machine, I expect Apache or nginx configuration. In one Ubuntu 7.10 task in InfraSet, I found that the agent had written its own HTTP server instead. Both websites worked, and the task received a perfect functionality score. But if I accepted that result, I would also inherit a new program to maintain.

This is the first example in my Illusion of Done series, following the earlier article. I want to show what can remain unfinished after an agent says the job is done, so you know what to look for.

What happened

Here is the original task prompt:

The documentation and purchasing teams need separate websites on node1, sharing TCP port 8080. Requests for docs.branch.test should serve the supplied docs tree; requests for orders.branch.test should serve the orders tree. An unknown Host header should receive an error rather than either team's content. The approved content is staged under /srv/legacy2/name-based-web-tenants; preserve it.

Keep the installed operating-system release and kernel; use software compatible with this legacy platform.

The agent created /usr/local/sbin/name-based-web-tenants.py. The execution log contains the command and source code: it uses Python’s HTTP server classes, adds hostname routing and file-path handling, and installs startup configuration so the service returns after a reboot.

The evaluation report records both sites returning the expected content, unknown hosts and cross-tenant file requests receiving errors, and unchanged content checksums. The service survived a reboot. That earned it 1.0 for functionality.

The task did not require Apache or nginx or forbid custom code. I have not established that either package was readily installable on this old system. So the agent met the stated requirements. What surprised me was how much new software came with the result.

The server is now your problem

This is what I mean by “crazy software”: you asked for two websites and ended up with a custom web server. If a URL behaves strangely next week, someone has to investigate that code. If you change it, someone has to test the change. You need to decide where the source lives, who maintains it and how fixes are deployed.

The passing tests do not answer those questions. They showed that the requested behavior worked and recovered after a restart. They did not establish how the server handles sustained load, slow clients or malformed requests. Those are untested properties, not defects demonstrated by this run.

Custom software may be acceptable to you. But that should be a conscious decision. The illusion of done is accepting the successful result without noticing the maintenance job attached to it.

What to check

My first check before accepting an agent’s work would be the process listening on the port and the command used to start it. In this case, that leads to the new Python server. Ask the agent which persistent programs it wrote and why. Read enough of the changes to tell whether it configured an existing service or implemented one.

If it created a service, make sure you have its source, know how to restart or remove it, and understand what was tested. Decide who will maintain it before treating the task as complete.

You can also set the boundary upfront: “Use an approved web server. If that is not possible on this machine, explain the blocker before writing a replacement.” That instruction was absent here.

I want the websites to work. I also want to know what I will have to keep working after the agent leaves.

Run details. Ubuntu 7.10, InfraSet scenario 8220, task name-based-web-tenants, batch 2026-10-03__01-23-07. The executor and separate LLM evaluator used gpt-5.6-sol at high reasoning effort. Evidence links above point to a fixed commit. This is one recorded case, not a claim about how often this happens.
