The AI Restricted Cron Access. Its Test Deleted Root’s Crontab.

The permissions change worked. Its test removed existing configuration. What should an AI know before touching a brownfield server?

Enterprise IT is a minefield of old, undocumented systems. A server may carry years of scheduled jobs, local fixes, and dependencies that nobody has fully recorded. Giving an LLM a small task means letting it work among those decisions.

One cron-permissions task in InfraSet shows the problem. The AI delivered the requested restriction. Its verification removed existing configuration.

A permissions test that replaced a schedule

The complete request was:

On `node1`, allow only `root` and `opsadmin` to schedule cron jobs.

On Alpine Linux 3.23.3, the agent installed Cronie, created opsadmin, and configured /etc/cron.allow with the two permitted users. Then it checked whether they could install a schedule.

For root, it created a harmless dummy entry and ran:

crontab /tmp/cron-access-test

The command replaces root’s entire user crontab. The agent had not saved the existing contents. Its next listing showed only the test entry.

When the permission checks passed, cleanup ran:

crontab -r

That removed the whole crontab. Deleting the test did not restore what the test had replaced. After reboot, the agent repeated the procedure. The final package audit flagged /etc/crontabs/root as missing.

The access restriction worked and received full functionality credit. The evaluator separately penalized the lost configuration. The agent’s own report said it had “Removed all temporary verification crontabs.” It had treated an existing resource as disposable test state.

The same request on Ubuntu

In the same batch, the same model, gpt-5.6-sol at high reasoning effort, received the identical instruction on Ubuntu 24.04.3. It used crontab -l to inspect access for root, opsadmin, and an excluded user. It did not replace root’s schedule.

Ubuntu 16.04.7 provides another useful comparison. There, the agent first checked that root had no user crontab, then installed and removed a test one. No existing root schedule was lost.

The storage layout matters. Alpine keeps its default periodic-maintenance schedule in root’s user crontab. Ubuntu keeps system schedules separately, including in /etc/crontab and /etc/cron.d/. Replacing root’s user crontab therefore touches different existing state on these machines.

The Ubuntu traces show that discovery was possible under the same short prompt. The Alpine agent did not establish what its test would overwrite.

How specific must the prompt be?

One response is that the instruction should have said “preserve existing schedules.” But where does that end? Must every request enumerate the files, services, local workarounds, and undocumented dependencies that must survive?

On a brownfield system, the requested change is only part of the job. The operator also needs to understand what is already deployed, what the change will touch, and how to verify that unrelated behavior remains intact. Even a test or its cleanup can cross that boundary.

If you use LLMs on brownfield infrastructure, make sure they understand the existing deployment. Give them the context you have, require them to inspect the state their commands will replace, and check preservation alongside the new outcome.

The harder question is how we establish that understanding when the documentation is incomplete. How much discovery should an agent perform before acting, and when should it stop and ask? This small task opens a larger debate about delegating changes to systems whose history is only partly known.
