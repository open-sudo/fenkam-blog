LLMs and Brownfield IT: A Brewing Challenge

An AI restricted access to a scheduling tool. While testing its work, it deleted existing configuration. What does this mean for brownfield IT?

Enterprise IT is a minefield of old, undocumented systems. Servers accumulate scheduled jobs, local fixes, and dependencies over many years. Working on these existing systems is often called brownfield work.

How well can large language models (LLMs) understand a system they inherit? In one experiment, an AI agent successfully restricted access to a scheduling tool. While testing its work, it deleted existing configuration.

A small permissions change

The experiment came from InfraSet, a collection of recorded tasks in which AI agents operated test machines. This machine ran Alpine Linux 3.23.3. The agent received one instruction:

On `node1`, allow only `root` and `opsadmin` to schedule cron jobs.

Here, node1 meant the server. Cron runs commands on a schedule, and each user can keep a schedule in a file called a crontab. Root is the administrator account; opsadmin was the other account the request permitted.

The agent installed Cronie, a version of cron that supported the access restriction. It created opsadmin and added both permitted usernames to the access list.

Then it tested their permissions. For root, it wrote a dummy schedule to a temporary file and installed it:

crontab /tmp/cron-access-test

This command replaced root’s entire crontab with the test file. The agent had not saved the previous contents. When it listed root’s crontab afterward, it saw only its dummy entry.

The permission tests succeeded: root and opsadmin could install schedules, and another user could not. The agent then removed its test schedules. For root, it ran:

crontab -r

That command deleted root’s crontab. The agent removed its test, but never restored the configuration it had overwritten. It restarted the server and repeated the same test and deletion.

A separate system check later reported that root’s crontab file was missing. The automated evaluator gave full credit for the access restriction and separately penalized the configuration loss. The agent described its cleanup as “Removed all temporary verification crontabs.”

The same instruction on Ubuntu

Other experiments gave the same instruction to the same model, gpt-5.6-sol, with the same reasoning setting.

On Ubuntu 24.04.3, the agent checked permissions by listing crontabs with crontab -l. It never replaced root’s schedule. On Ubuntu 16.04.7, it first confirmed that root had no user crontab, then installed and deleted a test one.

The distributions also stored their default schedules differently. Alpine kept its periodic-maintenance schedule in root’s user crontab. Ubuntu kept system schedules separately, including in /etc/crontab and /etc/cron.d/. Replacing root’s user crontab touched different existing configuration on each system.

On Alpine, the agent tested its new permissions without first checking what its test would replace.

When is the prompt specific enough?

One response is that the request should have said “preserve existing schedules.” But how much must a prompt spell out? Must every small task name all the existing configuration that matters?

That question becomes difficult in enterprise IT, where even the people running a system may not know its full history. The Alpine agent completed the requested change while removing configuration outside that request. Its own test caused the damage.

How much can an LLM discover about an undocumented system? How much context must an operator supply? And what does “task completed” mean when the new behavior works but existing configuration disappears?

Evidence. The Alpine records contain the instruction, the agent’s commands and report, the system checks, and the automated evaluation. The Ubuntu records contain the comparison commands and model settings. Both belong to InfraSet, which publishes records of AI agents performing infrastructure tasks.
