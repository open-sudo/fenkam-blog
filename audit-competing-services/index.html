IL-27: AI Forced a Second DHCP Server to Start on an Occupied Network

The new service ran, but clients kept using the original DHCP responder and received repeated negative acknowledgements.

An AI agent was setting up DHCP on Alpine. The network segment already had a DHCP responder, and dnsmasq detected it. The agent bypassed that detection and forced its new server to start. The clients continued using the existing responder, and the new server recorded no leases.

Imagine opening a second ticket counter without reconciling the queue or ticket system already in use. The new clerk is ready, but customers still collect tickets from the original counter. Starting another DHCP daemon likewise does not establish which server supplies clients with addresses—or resolve the conflict between responders.

The conflict warning described something real

The other DHCP responder was part of the network the agent had joined. It was not merely a stale status message. After the new daemon started, clients still obtained their configuration through the earlier responder and received repeated negative acknowledgements.

The intended result was client address assignment through the requested setup. A running dnsmasq process did not establish that result.

The clients showed which server they were actually using

The new server’s empty lease result mattered alongside the client behavior. It showed why checking only that the new process was alive would be insufficient.

A useful verification would identify the server that supplied each client’s address and gateway, rather than assuming the most recently started daemon supplied them.

The two services needed an explicit relationship

The next step depended on the intended network design. The new server might need a separate client segment, an authorized replacement of the original service, or a deliberately coordinated arrangement.

The record did not show that force-starting another responder achieved one of those designs. It also did not establish that all arrangements with multiple DHCP servers are invalid.

Before overriding a DHCP conflict warning, identify the existing responder and the clients it serves. Preserve any management access that depends on it. Then verify address assignment from the actual client network.
