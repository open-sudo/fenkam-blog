The New DHCP Server Entered a Segment That Already Had One

One recorded deployment bypassed another-server detection, while clients continued using the existing responder.

An agent tried to start DHCP on a segment that already had a responder. It bypassed the warning and forced the new service to start. The clients continued using the existing server. This is one recorded conflict, with a useful distinction between starting a daemon and actually providing addresses.

A conflict warning was treated as an obstacle

The agent bypassed dnsmasq’s other-server detection and forced DHCP startup on a shared segment. Clients kept using the existing responder, produced repeated negative acknowledgements and created no leases on the new server. (commands.)

The existing responder was part of the network the new DHCP service entered.

A running daemon did not establish lease ownership

The recorded clients continued using the prior responder. Repeated negative acknowledgements and an empty lease result from the new service provided evidence about actual assignment behavior, beyond whether its process had started.

The intended topology needed reconciliation

The useful next question is whether the task expected a separate client segment, replacement of the original responder or a deliberately coordinated arrangement. The available record does not establish that force-starting a second responder fulfilled any of those designs.

What should an administrator check?

A DHCP handover needs evidence of which server assigned the client address and on which segment. It should preserve an existing management-network service unless the task authorizes its replacement. This case illustrates a conflict in the observed lab topology; it does not establish that every multi-server DHCP design is invalid.
