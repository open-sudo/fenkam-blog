IL-29: AI Started a Competing DHCP Server

The agent bypassed dnsmasq’s warning. Clients still used the existing DHCP responder.

I wanted an Alpine machine to supply DHCP settings to its clients. I gave the setup to an AI agent. When it tried to start dnsmasq, the DHCP service, the program refused because it detected another DHCP server on the same network segment.

The warning called for a check of which server should assign the clients’ addresses. Instead, the agent bypassed the detection and forced the new dnsmasq process to start.

The clients continued using the existing server

The process was running, but its lease list was empty. Checks on the clients showed that they still obtained their configuration through the earlier responder and received repeated negative acknowledgements.

The existing responder was real, rather than a stale warning that could simply be ignored. Verifying the new service required identifying which server actually supplied each client’s address and gateway.

Recorded commands

The correct repair depended on the intended network design: separating the client segment, replacing the old service with authorization, or coordinating the two servers. The record did not show that force-starting dnsmasq achieved any of those arrangements. It showed a new daemon running without demonstrated service to its intended clients.

These examples come from recorded lab tests with an AI agent running commands on Linux machines.
